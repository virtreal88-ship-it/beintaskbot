# Owner-confirmed direct dialogue identity

An unknown WhatsApp LID and a phone route can represent the same person even when no signed LID/phone pair has been saved. A company owner may explicitly identify that exact pair. This is an owner assertion, not provider verification.

`whatsapp_dialogue_owner_merge_preview` accepts the exact canonical/source lead IDs, international phone and reference to the owner's explicit confirmation. The canonical route must already have that one provider-proven phone; the source may lack phone proof, but may not contradict it. Both routes must belong to the OAuth company and channel. Every provider conflict remains blocking, including historical split flags. Names, avatars, numeric LID suffixes and editable phone fields never substitute for confirmation. Existing assignment, hold, in-flight-job and draft safeguards still apply.

`whatsapp_dialogue_owner_merge` requires the same arguments, a fresh actor/scope/evidence/dependency precondition, UUID request ID and `confirm=true`. It uses the existing `ai_learning.dialogue_merge` scope and rechecks the live owner role. It records an immutable assertion receipt with source `owner_assertion`, actor, server timestamp, exact pair/phone, evidence reference and rollback mapping. It creates the retained route link atomically with the audit and idempotency receipts. Concurrent identical requests commit once. No messages, media, analysis, CRM records or source routes move or disappear; no model or send is invoked.

Provider alias rows are untouched. Ingestion resolves provider facts first, then applies the owner route overlay while retaining server-controlled provider conversation and assertion IDs. Employee recognition, native contact identity and phone evidence use the provider identity, not the owner-selected route. Consequently an unpaired LID receipt cannot make `provider_phone_proven` true. A later genuine signed pair can independently supply that proof. New contradictory provider evidence quarantines the canonical and retained source routes, including replayed events. Owner links never clear provider quarantine.

The normal duplicate preview exposes the owner merge and preservation checks. Existing `whatsapp_dialogue_merge(operation="rollback")` deactivates the link and revokes the assertion after the existing control freshness checks. It preserves the historical assertion, source rows, all later messages and independently learned provider aliases. A replay of an old merge request returns its original receipt without reactivating a revoked merge. A fresh re-merge requires a new explicit confirmation and preview.

Validation uses disposable localhost PostgreSQL and mocked provider/model calls: full retained history/case/media journey; exact role and tenant/channel isolation; stale confirmations; concurrent retries; atomic audit failure; provenance injection attempts; unpaired LID ingestion without employee/phone proof; new signed proof; contradictory replay; and rollback with later evidence/history. Deployment alone does not merge production data: the exact pair must pass the supported preview and apply tools after release.
