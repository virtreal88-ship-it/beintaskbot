## Архитектура

Остаётся один продукт Beintaskbot. Worker владеет авторизацией, источником, CRM, AI и долговечными бизнес-операциями. Внутренний Go-процесс отвечает только за WhatsApp Web/медиа и использует **один client/sqlstore на подключённый номер**. Python supervisor управляет приватными процессами/хранилищем. Это внутренний компонент уже существующего Railway whatsapp-calls, не новый обязательный Connect и не дополнительный QR.

Новые процессы/диски/тарифы сейчас не создаются. Достаточность действующего 1 CPU/1 ГБ/диска нельзя обещать без замеров нескольких источников; увеличение ресурсов требует отдельного решения.

### Долговечность и единственный владелец

1. Эксперимент использует существующий runtime flock и один приватный диск. Этот lock защищает конкурирующие процессы **с тем же диском**, но не два клона диска на разных узлах. Масштабирование владельцев пока запрещено.
2. До production-переключения нужен durable source mode/generation и выдача полномочий только после прекращения старого процесса. Истечение короткого lease не доказывает прекращение WhatsApp-соединения. Новая реплика не подключается, пока старое владение не ограждено на уровне процесса/тома.
3. Входящее сохраняется до подтверждения обработки; доставка Worker повторяема, Worker подтверждает только после transaction commit. Durable event ID включает source scope и provider identity. Учитывать отдельно receipts/history/group events: одинаковый код callback не гарантирует одинаковую семантику ack у провайдера.
4. Перед отправкой сохраняются operation ID, выбранный источник, точный адресат, хэш содержимого и заранее выделенный provider message ID. Если send уже начался и результат неизвестен — вернуть unknown, не вызвать send повторно. Повтор операции с другим содержимым/адресатом — conflict.
5. Поздние события старого поколения не меняют нового владельца. Они сохраняются для контролируемой сверки, а не молча удаляются и не превращаются в новые отправки.
6. У текущего Worker `external_id='connect:'+data.id` часто означает **внутренний ID Connect**, а provider ID хранится в raw.externalMessageId. Поэтому нельзя просто переключить external_id на WhatsApp ID: нужна точная таблица соответствий/поиск доказанной связи, иначе появятся дубли.

### Защита данных

Действующие tenant/source/operator guards остаются серверным авторитетом. Внутренний транспорт не принимает tenant/account из произвольного тела браузера. Сессии — приватный том, права файлов, без копирования ключей в логи/ответы. Новый журнал полезной нагрузки — с аутентифицированным шифрованием и ключом вне БД. Для каждой выдачи media/recording проверяются текущие права и принадлежность источника. Протокол не получает права писать клиентам в обход Worker.

## Этапы и критерии перехода

1. **Аудит и лабораторный компонент** (текущий этап): перечень контрактов/лицензий; выключенный эксперимент на существующем движке, изолированные тесты. Рабочие номера не затрагиваются.
2. **Живой тест тестовый**: отдельная прежняя VM и согласованный участник. Проверить реальный номер сессии перед отправкой. QR → текст обе стороны → файл/voice → тестовая группа/участники/receipts → входящий и исходящий звонок не менее 3 минут, сообщения/вложение во время звонка, запись обеих сторон. Не использовать клиентские диалоги. Отдельно проверить отсутствие сети, повторное подключение и рестарт. Зафиксировать номера только маскированно, SHA, время, счётчики и результаты.
3. **Адаптер Worker за флагом**: существующая карточка/QR intents/права/проекция; два синтетических tenant, несколько источников, конкуренция и восстановление. В production флаг выключен, пока все обязательные функции не подтверждены.
4. **Подготовка рабочий A**: согласованный момент, экспорт точных mappings/счётчиков/очередей и резервная копия. Сохранить ID `work-source-A`, историю, права, назначения, AI. Сначала остановить legacy отправки/AI для этого source, дождаться или явно удержать unknown операции; остановить старый протокольный owner, затем разрешить native. Возможно повторное сканирование QR; совместимость сессии Evolution не предполагается.
5. **Откат**: quiesce native, дождаться доказанного закрытия/ограждения, сохранить все новые события/медиа/receipts и mapping в Worker, затем восстановить legacy owner. Не откатывать CRM-БД к старой копии, не повторять unknown sends. Дочитать старую очередь по поколению и provider ID; не терять сообщения, полученные после переключения.
6. **Остальные номера**: каждый отдельно с наблюдением и готовым откатом. Только после всех зависимостей/потребителей и отдельного согласования — вывод Connect/Evolution и удаление данных. До этого сохранять конфигурацию, историю и сессии.
