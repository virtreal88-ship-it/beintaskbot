# Непрерывная внешняя проверка CRM

Этот наблюдатель не требует отдельного платного ПО, но ему нужен **уже
доступный постоянно работающий Linux-хост вне production Railway**.
Наличие файлов не означает, что монитор запущен. На ноутбуке, который может
уснуть, требуемого покрытия не будет. Если независимый хост недоступен,
оставьте текущую проверку GitHub Actions включённой как резерв:
её расписание выполняется нерегулярно.

## Что проверяется

Раз в 30 секунд делается внешний HEAD к `https://crm.pro.az/health` с
тайм-аутом до 5 секунд. Нужны одновременно HTTP 200 и
`X-Beintaskbot-Health: worker`. После непрерывной минуты ошибок отправляется
одно сообщение. После первого успешного ответа добавляется сообщение о
восстановлении, если Telegram подтвердил сообщение о сбое. Долгий пробел между
пробами сбрасывает неподтверждённую серию ошибок. Локальная SQLite сохраняет
решение между рестартами; при неизвестном исходе отправки исходное сообщение
повторно не отправляется. Никакие клиентские данные или журналы не передаются.
Это проверка публичной доступности Worker, а не доставки сообщений или
доступности конкретного CRM-раздела.

## Включение на уполномоченном хосте

1. Используйте Python 3 и systemd c поддержкой `LoadCredential`. Запустите
   `python3 -m unittest discover -s ops/crm-availability -p 'test_*telegram_monitor.py'`.
2. Установите `continuous_telegram_monitor.py` и `telegram_monitor.py` как
   root-owned read-only файлы в `/opt/crm-telegram-observer/`. Положите
   `crm-telegram-observer.service` в `/etc/systemd/system/`.
3. Через одобренное хранилище секретов заполните два root-only файла с правами
   0600: `/etc/crm-telegram-observer/telegram-bot-token` и
   `/etc/crm-telegram-observer/telegram-chat-id`. Используйте только
   подтверждённый личный чат владельца. Не копируйте значения в исходники,
   командную строку, логи или общий чат.
4. Проверьте доступность хоста и Telegram отдельно до переключения. Сначала
   проверьте оба сообщения на тестовой цели с тестовым получателем, не ломая
   production и не отправляя тест клиенту. Затем запустите production-цель
   командой `systemctl enable --now crm-telegram-observer.service`. Для
   постоянной работы проверьте службу и внешнюю видимость журнала. Потерю
   самого наблюдателя этот процесс не может заметить; она требует отдельного
   наблюдения за хостом.
5. Не оставляйте два production-отправителя в одном личном чате: после
   подтверждения готовности перенесите доставку с GitHub Actions на этот
   наблюдатель в окно, когда CRM здорова и активного инцидента нет. Откат:
   остановить службу, восстановить старый workflow. Не удалять checkpoint
   во время инцидента.

Монитор не перезапускает CRM.
