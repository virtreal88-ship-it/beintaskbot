# Контекст и архитектурные правила проекта [Название Проекта]

Этот документ содержит ключевые правила, архитектурные гайдлайны и контекст для AI-ассистентов. Все изменения в коде должны строго соответствовать этим принципам.

---

## 1. Стек технологий и окружение
* **Язык / Фреймворк:** [например, TypeScript, Node.js v20, React 18 / Next.js 14]
* **База данных / ORM:** [например, PostgreSQL + Prisma]
* **Стейт-менеджер / Запросы:** [например, Zustand / TanStack Query]
* **Стиль / UI:** [например, Tailwind CSS + shadcn/ui]
* **Тестирование:** [например, Vitest, Playwright]

---

## 2. Структура проекта и зона ответственности
* `/src/components` — Чисто презентационные UI-компоненты (без бизнес-логики).
* `/src/services` — Вся бизнес-логика и внешние API-вызовы.
* `/src/db` — Схемы и запросы к базе данных.
* **Правило связей:** Компоненты НЕ вызывают БД напрямую. Все данные проходят через сервисный слой (`/services`).

---

## 3. Критические правила (Инварианты) — ЧТО НЕЛЬЗЯ ЛОМАТЬ
1. **Типизация:** Запрещено использовать `any`. Все функции и API-ответы должны быть строго типизированы.
2. **Логика БД:** Никогда не удаляй и не переписывай существующие миграции. Изменения схемы — только через новые файлы/поля.
3. **Обработка ошибок:** Все асинхронные вызовы и ручки API должны быть обёрнуты в `try/catch` с единообразным логированием через `logger.ts`.
4. **Совместимость:** Существующие публичные API-контракты (`/api/v1/*`) не должны ломаться без явного согласования.

---

## 4. Кодстайл и паттерны
* **Стиль:** Функциональный подход, чистые функции без побочных эффектов, где возможно.
* **Именование:** `camelCase` для переменных и функций, `PascalCase` для компонентов и типов, `kebab-case` для имён файлов.
* **Размер файлов:** Один файл — одна ответственность. Если файл превышает 200–250 строк, предложи его декомпозицию.

---

## 5. Инструкции для AI при выполнении задач
1. **Сначала план:** Перед генерацией кода для любой новой фичи сначала предложи краткий план реализиции, подсвети риски для текущего кода и дай 1–2 идеи по улучшению/оптимизации.
2. **Точечные правки:** Менять только те файлы, которые относятся к задаче. Не переписывать соседний код «попутно».
3. **Самопроверка:** Перед выгрузкой кода проверь:
   - Добавлены ли необходимые типы?
   - Не сломаны ли связанные импорты?
   - Обработаны ли крайние случаи (edge cases, `null`/`undefined`, сетевые ошибки)?
