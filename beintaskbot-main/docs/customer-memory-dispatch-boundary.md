# Customer Memory: model dispatch and delivery boundary (research; not integrated)

This note describes a possible future contract, not an implemented or approved adapter. Customer Memory remains disabled. `tenant_customer_memory_agent_preview.preview` is a staff-only, non-dispatchable diagnostic; it must not be passed to a model, used to authorize a send, or cached as an agent projection.

## Existing boundaries

* In `tenant_chat_ai_provider.generate`, `before_dispatch(wire)` runs before the synchronous `requests.post`. The callback has returned before the HTTP request begins; its own completed SQL transaction cannot make a later external request atomic with deletion or revocation.
* The Connect worker calls `generate` twice on some paths. Both invocations have media callbacks, but neither validates memory. The Kommo path has separate initial and retry calls, and no memory callback. Expert/no-answer and policy-reply paths must be audited separately before they can use or forward memory-derived content.
* `tenant_connect_transport.send_ai_reply_if_active` takes dialog/state locks and validates existing scope/media before its Connect request; `tenant_ai_agent_send.send_agent` similarly protects its final Kommo POST with dialog, job, settings and receipt checks. Those locks do not currently cover memory, its source ACL, CRM subject identity, or their revocation. A new SELECT in `route_and_send` would not change that.
* Existing agent assignment/version, live job, mandatory media and source checks remain mandatory. Optional memory failure cannot weaken them. A worker without a supported principal/source ACL must receive no memory.

## Required semantics and unresolved atomicity

A candidate projection must be bound to tenant, verified subject and identity-link version, requested conversation/channel, authenticated principal and current source-level permissions, exact selected source/message versions, fact and deletion/revocation revisions, and the assigned agent/configuration version. Only authorized, current facts can be selected before a projection or summary is made. The reference passed among internal components should contain identifiers/versions and a keyed integrity check, not raw deleted facts, secrets or an unscoped cache key. Every caller must treat the projected text as untrusted data. A client report remains a report, not proof of its claimed cause. Expiry/freshness rules and the automatic agent service-principal permissions are not yet established.

A pre-dispatch recheck alone has a race: it can commit, a deletion or ACL/identity revocation can commit, and then the same worker can transmit stale context. A second check after generation alone has the same race before customer delivery. The synthetic tests demonstrate both. SQL transactions cannot atomically commit with a third-party HTTP POST: a separate database SELECT, or an outbox intent committed before the network call, is insufficient. An accepted network request cannot be recalled if revocation occurs afterward.

A strong linearization contract could serialize *all relevant* invalidations with a guard held until the outbound request has been admitted, then repeat that guard at final delivery and discard a draft if invalidated in between. If erasure commits first, no affected dispatch/delivery may begin; if admission wins, the in-flight request began before erasure became effective. This describes a possible ordering, not a safe deployable implementation. It must define exactly what “admitted” means; `requests.post` does not expose a verified atomic provider-admission callback, and holding PostgreSQL row/advisory locks over the full request can stall existing contact/source deletion, deadlock across subjects/channels, and fail under network delay. The current channel fence already has a known CRM deletion regression. Do not reuse it for AI dispatch.

Achieving both nonblocking existing CRM deletion and a stronger promise that no already-started provider operation can complete after deletion requires an explicit cancellation/erasure-completion protocol and provider or trusted transport support; a local stale-context check cannot provide that promise. Options must specify pending versus completed deletion, crash recovery, unknown request outcomes, bounded waits, and what the operator sees. Do not silently weaken the deletion semantics or claim atomicity. A lower-risk interim is no memory in model requests or generated replies.

## Integration work once the boundary is approved and independently reviewed

1. Provide a server-only principal-scoped projection with explicit statuses (no memory, ambiguity, denial, temporary failure), no hidden-source counts and a genuine end-to-end bounded timeout. Resolve the agent service principal through an existing authorized scope; do not invent owner permissions. Apply customer/source ACL before selecting or summarizing, and fail closed on unknown identity or incomplete ACL.
2. Introduce a single memory guard/receipt interface at the actual outbound transport boundary. Revalidate tenant, source versions/access, identity membership, deletion fences, assignment and agent configuration under the same reviewed invalidation protocol, for **each** initial and subsequent model invocation. The guard must bind the actual untrusted projection used in the wire. Do not hold CRM/source locks across an unbounded provider response.
3. Mark any generated draft that used memory with its scoped, opaque receipt. Immediately before every customer or other external delivery path, revalidate it using the same protocol in the existing final-send boundary; if changed, suppress the entire draft. Do not use an old draft as a substitute for missing current-case/media evidence. Policy and retry paths must either be proven memory-free or carry the same receipt.
4. Preserve existing spend reservation and usage accounting. Record known completed usage even when an invalidated draft is suppressed; if provider outcome is unknown, keep it unknown and do not trigger an automatic paid retry. Memory token use belongs to the existing request, without double billing.
5. Test real PostgreSQL interleavings involving actual source/fact delete, edits, permission changes, assignment changes, identity splits, tenant separation, in-flight generation and every delivery path, as well as bounded/unreachable provider and process crash. Fake callback tests below prove only the general ordering, not these product integrations. Independently review lock ordering and measure CRM availability and latency before enabling anything.

`tests/test_customer_memory_dispatch_boundary.py` uses an isolated PostgreSQL schema and synthetic callbacks. It illustrates the race, an erasure-first denial, the ordering obtained by a transaction-held shared row lock, and a revoked-during-generation draft being dropped. The locked demonstration intentionally delays deletion; it is not a candidate production mechanism. No real provider request or customer message is made.
