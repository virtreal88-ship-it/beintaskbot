# Support and admin workflow audit

This audit is a desktop-only map and implementation plan. It does not change live data, grant, agent configuration, or model settings.

## Current user-facing paths

| Work | Current UI / API | Current constraint that creates extra steps |
|---|---|---|
| Support conversations | Dialogs workspace; `/api/platform/ai/dialogs`, `/dialogs/history`, `/dialogs/agent-assignment`, `/dialogs/agent-assignment-bulk` | Assignment is a separate operation from conversation review. The backend returns allowed agents, route scopes, revision, and a reason when no exact assignment is valid; the UI must surface that reason rather than imply a generic failure. Group coordination uses a separate registry. |
| Support cases and knowledge | Support Cases workspace; `/knowledge-candidates`, `/boundaries`, `/source-review`, `PATCH /{candidate_id}`, `/approve`, `/reject`, `/archive`, `/restore`, `/mark-knowledge-published` | Owner edits, result confirmation, knowledge publication, case status and existing published knowledge are separate paths. The case list is keyset-paginated (50/page); rejected, archived, and knowledge-published are hidden by default and filterable. A separate campaign panel is being moved from Settings into this workspace. |
| Case media analysis | Case attachment admission opens the existing campaign flow; campaigns preview, prepare, owner-approve, start, pause/resume, and spend ledger use separate APIs | Eligibility, scope, model/tariff, source-version and unknown-attempt guards are backend enforced. The owner sees overly technical steps. The one-time grant is limited to an existing-case snapshot; a $10 total prospective cap does not clear old unknown holds or authorize future cases. |
| AI agent create/edit | AI Agents workspace; `/agents` and `/agents/{agent_id}` | The workspace and settings are split. Changes that affect active behavior must retain their current approval/version guards and preview impact in one clear confirmation. |
| Agent removal | `GET /agents/{agent_id}/delete-preview` and exact-confirmed `DELETE /agents/{agent_id}` remove the selected agent configuration. | The preview reports paused/unassigned dialogs, stopped queued jobs, active work and retained history. Processing jobs and active campaigns block removal. Published knowledge, CRM messages, spend/audit receipts and AI history remain under a minimal non-secret identity record. The legacy archive/transfer service remains a separate explicit operation. |
| AI configuration/training | Agent settings, knowledge center, instruction library, administrator review and MCP administrator tools | Draft, owner review, apply, post-apply publication, and rollback are deliberately distinct for sensitive material. Keep that distinction where it changes active behavior; collapse redundant navigation and show the next valid action/status on the same screen. |
| CRM work | Tasks, customers, companies and deals; native and Kommo-backed entities appear together in several workspaces | CRUD already exists in the desktop CRM. Keep ordinary CRUD direct; show an impact summary only for actions that change/delete linked records. Do not combine separate record types or silently alter synchronization. |

## Plugin capability matrix

The existing MCP service (`tenant_ai_learning_mcp.py`) has scoped read, case-media preflight/single-message, direct reconciliation, dialogue merge, duplicate-knowledge preview/archive/rollback, training review, administrator draft/apply/rollback, and publication-review tools. Those administrator tools prepare or apply their exact approved draft types; they are not an unrestricted proxy to the web API.

| Owner action in the desktop app | Existing plugin coverage | Gap for a complete plugin workflow |
|---|---|---|
| Read cases, status/history, source boundaries | `support_cases_list`, `support_case_detail`, and `support_case_delete_status` provide tenant-owner case reads, bounded keyset pagination, explicit status filters and exact deletion-receipt checks under `ai_learning.support_cases`. `support_case_edit_boundaries` uses the same versioned owner mutation as desktop. | Broader extraction history remains available only through the desktop workflow; plugin reads are not yet a full case-analysis ledger view. |
| Suggest or change case boundaries | `support_case_edit_boundaries` now forwards the exact candidate/version/start/end IDs to the existing owner-only boundary mutation; the server revalidates the route, interval and retained outcome/cause evidence, then audits the change. | Plugin boundary discovery remains read-only case detail; proposal UX can select known IDs from that detail, and existing service rejects stale versions or evidence loss. |

The MCP surface must call the same existing services as the browser. Its error mapping should distinguish missing scope, route incompatibility, unavailable media, provider HTTP failure, and unknown spend; it cannot promise model access or override a provider denial.

## Attachment coverage contract

Current bounded extraction handles images; audio/voice via cached transcript or optional paid ASR; video via sampled frames and optional ASR; and documents for text/PDF/DOCX. PDF processing extracts text first and can render at most two pages for a bounded visual fallback. XLSX/other spreadsheet, encrypted/unreadable files and unsupported MIME types must remain explicitly unsupported unless an existing parser is wired. Code limits include four files, 20 MiB non-video aggregate, 10 MiB audio, up to two visual observations, and video limits of 100 MiB/120 seconds. A sampled video is partial temporal coverage. Current code may skip an item after time/file/model limits; each item must therefore retain an explicit status/reason, and the case must never be labeled fully analyzed if any in-boundary item is pending, partial, unsupported, unavailable, truncated, or failed. Preserve page/frame/time provenance and distinguish transcript text from observation/inference.

## Simplified target flow

1. One desktop queue is the home for cases, review state, and analysis readiness. Filters include all hidden/rejected/archived/published statuses; pagination and counts use server-side cursor metadata.
2. A case card shows one suggested interval, customer problem, facts vs assumptions, final customer evidence/outcome status, attached-source inventory, and a short plain-language media coverage warning. Owner adjusts start/end inline when needed.
3. One existing owner grant previews the exact existing-case snapshot, enabled parsers/models, current $10 prospective pool, existing tenant cap, known spend, and old unknown holds. Start is one owner action after that impact preview. Revoke blocks future calls. No future-case scope or automatic retry is implied.
4. Reuse exact-version cached receipts. For a previously unknown attempt, admit at most one explicit new attempt for the exact current tenant/channel/message/version/hash under the shared grant; preserve the old hold and stop if the new attempt is unknown. Missing historical projection is not evidence that a provider was never called.
5. Review once: “Save and publish guidance” publishes useful owner-reviewed material with cause/result status labels intact, including an unknown outcome. “Approve confirmed resolution” remains governed by the current confirmation rules. “Reject and delete” permanently removes only the selected case after an exact-target, action-time confirmation that the case cannot be recovered; it must never substitute an archive. If published knowledge is linked, the same confirmation must explicitly choose whether to retain it as an independent owner source or deactivate it. Original CRM messages and unrelated sources are never cascaded.
6. Assignment and agent removal are presented beside the relevant conversation/agent. Removal shows exact impact, requires one final exact-target confirmation, pauses and unassigns dialogs, and never starts a replacement. Existing tenant, owner, version, audit and paused-state rules remain in services.
7. The MCP plugin mirrors these same typed operations; it does not provide blanket powers, raw database access, agent activation without approval, outbound messaging, or a provider retry bypass.

## Reusable analysis artifacts are the primary architecture boundary

Keep three independently versioned layers: (1) raw-media component analysis, (2) structured case facts/boundaries with source attribution, and (3) owner-published knowledge. A case edit or publication must read existing compatible artifacts and must not call vision/ASR again. Reuse identity includes tenant, exact verified content hash, component, model/config version, and language; two messages with equal bytes may share an authorized tenant artifact while retaining separate message/case attribution. A single-flight reservation must be atomic across workers. Store completed components separately so a failed PDF page or ASR component does not repeat completed vision/text work. An unknown billed attempt keeps its hold and is never silently retried. Recompute structured facts only when its actual inputs or extraction instructions changed; label the changed input/version and cost-impact before a new paid analysis.

Permanent case deletion must remove the case payload and its case-specific source/review snapshots, not hide them in an archive or orphaned analysis cache. Retained analysis artifacts need explicit tenant authorization, references and expiry/lifecycle; do not retain a deleted private case's raw transcript, extracted document content, or claims merely to improve cache hit rates. Preserve independently published knowledge only through an explicit action-time choice and convert its provenance to a standalone owner source; otherwise block case deletion until the owner chooses. Never delete original CRM messages or unrelated analysis/spend/security receipts as part of case deletion.

Agent-history migration redirects references from the full agent configuration row to `saas_ai_agent_history_identities`, which stores only the tenant, agent ID, display name and deletion actor/time. Historical FK references remain valid after physical removal of the configuration row. Rolling back the schema migration requires restoring old FKs only after every referenced agent ID exists in `saas_ai_agents`; deleted IDs cannot be reconstructed as runnable agents from this minimal identity row. A database rollback must not recreate instructions, secrets, model settings or enabled state from history.

The checked-in FK dependency map is explicit: jobs, runs, token usage, drafts, action runs, expert-task principal/expert references, isolated test sessions, knowledge campaigns, and published case-to-agent links move to the minimal identity table. The delete service first refuses active jobs/runs/actions/test turns/expert tasks/campaigns; it then skips queued jobs, rejects unsent pending drafts, and pauses/unassigns dialogs. Triggers and no-answer runtime state are deleted; group bindings are removed and paused; other agents' expert references are detached, with expert-call triggers disabled if their target was removed. Simulation config is stopped and detached. CRM conversations/messages, completed run results, token/spend receipts, draft contents, test history, stopped campaign records, published knowledge and audit history remain. No agent prompt, credentials, model config or enabled state is copied into the history identity.

## Acceptance gates

- UI → API → storage journey for a mixed printer case with a customer photo caption, a reused completed photo, stale/unknown prior attachments, suspected cause, and unknown result. Guidance can be published without upgrading uncertainty; ordinary resolution approval still rejects it.
- Text-only owner-provided guidance can publish while outcome remains unknown. Rejection hides the card and restore recovers it; no history/source row is deleted.
- Snapshot contains every in-boundary media item; partial/unsupported/encrypted/truncated/media-access/model/budget failures are visible with a next step. Test PDF text and rendered-page references, DOCX, supported image/audio/video, and explicitly unsupported spreadsheet fixture.
- Exact receipt reuse has no provider call or second reservation; one explicit current-version retry keeps prior unknown hold; changed hash, channel, tenant, or candidate boundary blocks before provider; concurrent claims cannot exceed $10 or tenant cap.
- The same file in two messages/cases reuses one tenant-authorized artifact while preserving separate provenance; changed bytes or model/config cause a new component; concurrent work is single-flight; crash recovery resumes only missing components; partial completion, unknown attempts and retries do not duplicate completed work.
- Publishing twice and editing/rebinding a case do not re-run extraction; changed case input/instructions display the exact reason for a new extraction. Report cache hits and avoided calls without claiming invented dollar savings.
- Case queue with 100 synthetic items paginates/counts consistently and defaults out rejected, archived and knowledge-published while filters recover each state.
- Exact-target case deletion tests that only the selected case payload/review snapshots are removed, dependency choices are explicit, linked knowledge is retained independently or deactivated only by explicit choice, unrelated CRM/source/spend/security records remain untouched, and no hidden case-content cache/archive survives.
- Desktop case UI and plugin typed operations test owner/non-owner, tenant isolation, source/version conflicts, double click and idempotent replay. The permanent-agent-delete service and plugin test exact-target/version confirmation, dependency conflicts, history preservation and paused state; PostgreSQL CI covers assignment/deletion races. Slow-provider browser behavior and live post-deploy owner smoke remain release gates, not locally verified claims.
- Full browser smoke uses deterministic provider mocks only. Real provider access and real-media analysis require a separate owner run; a deployed feature/configuration is not a completed real analysis.
