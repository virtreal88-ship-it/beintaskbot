# Customer Memory: audit and implementation boundary

Audit base: `fc75c2899b7b86de42bf2cafdbdd116e9717d821` (2026-11-03). This is a code audit of selected paths, not a production or data-quality audit. The current draft installs additive tables, triggers and dormant APIs but does not call AI, change agent contexts or enable campaigns. It is a prototype and must not be merged or deployed.

## Existing mechanisms and limits

## Required integration design

* Keep subjects separate: native contact, native company, and a real existing object when a suitable entity is established. A group or case can retain facts in its own scope without attributing them to an unverified organization or person. Record the message author independently from the subject.
* Persist source references and temporal fields separately from facts: event time, observation time, validity interval, last confirmation, provenance kind and reliability. An AI proposal starts as requiring review; repeating it does not establish a cause or confirmation. Case status, assignee and next action are read from the current case/task, not maintained as a competing registry.
* Source and subject membership must be revalidated on read, and identity link changes, source access revocation, edits and deletion must fence in-flight work and derived contexts. The present mapping lacks a complete versioned history and reassignment workflow. Until a trustworthy binding and invalidation boundary exist, do not expose cross-dialog personal projections.
* Within one transaction, lock and compare memory, identity and source versions before applying work; a later AI result is stale when any changed. A deletion suppresses re-extraction from that source and subject without retaining the deleted value, and invalidates every derived representation. Keep correction and do-not-store semantics distinct. Hashing an arbitrary secret does not make a tombstone safe: use non-content source/subject identifiers and protect their access.
* Source ACL filtering happens before selecting facts, summary, count, search, version or export. Do not share a prebuilt all-source summary across principals. The future reader takes tenant, verified subject, conversation, assigned agent and authenticated user/service principal and returns only authorized facts, source references, freshness/version and incompleteness. It distinguishes no memory, ambiguous identity, denial and temporary error. Reading never launches a build or AI call. Never return existence metadata from inaccessible sources.
* Memory text is untrusted evidence, not instructions. Use an independent bounded read timeout and context budget. Fail open only for a memory outage, retaining all existing identity, access, assignment and mandatory current-media gates. Do not include secrets or raw conversation history in memory, logs, tombstones or external prompts.
* Feature flag defaults off per tenant. Backfill is independently disabled and requires an explicit, bounded grant. Use existing budget reservations, limits, source fingerprints, checkpoints and unknown-outcome fencing; do not run on deployment or analyze media again. Batch delayed messages and revisit a source when saved transcription evidence arrives. No private Copilot conversations as sources.

## Delivery and verification gates

## Current draft and outstanding release blockers

The draft supports manual facts for an explicitly owner-confirmed direct contact route. Each requires an exact evidence quote and an acknowledgement; multiple facts per source and explicit shared-claim groups are supported. Reads recheck employee permissions, route identity, source fingerprint and link versions. The contact-card UI exposes evidence selection, manual edits, version conflicts and deletion. It has no AI adapter, automatic extraction, summary, case projections, company/store/group subjects or media receipt support. Assertions about factual accuracy cannot be established by synthetic tests. Sensitive-text filtering is incomplete and cannot guarantee absence of secrets.

The feature requires both a process and tenant flag, and is disabled by default in code. Production flag state was not checked. Existing CRM phone matching is not proof of person identity. Source and contact erasure use opaque keyed fences; channel-wide fencing is conservative and can hide unrelated contacts indefinitely. It lacks reviewed recovery and key rotation. Deletion of a contact while a memory operation holds the channel gate can currently fail with PostgreSQL 55P03, including after disabling the flag. The trigger is installed independently of the flag. This is a **release-blocking CRM regression**, not an acceptable erasure design. A trial using blocking exclusive gates was also rejected: independent real-PostgreSQL review reproduced a deadlock (40P01) when concurrent transactions delete contacts across two channels in opposite orders. It was reverted; the deadlock does not describe the current checked-in try-lock implementation. The optional message-ingest trigger also requires review and measured production impact.

The internal non-dispatchable agent preview checks staff, route and assignment and filters to confirmed in-date facts. It is restricted to the current direct conversation, does not prove current factual quality, and does not enforce a hard end-to-end deadline. The existing staff memory read can return non-current statuses. It is not safe for an AI principal. Committed deletion/revocation after read is not yet fenced through external model dispatch and final delivery. Do not connect it to agents or claim a working voice adapter. Source-level ACL, assignment, current case/media evidence and prompt-injection controls must be enforced independently before any integration.

Disposable PostgreSQL, local HTTP and desktop/mobile Chromium tests validate only exercised synthetic cases. Further independent review, real multi-transaction race tests, latency measurements, backwards compatibility, exact-head CI and permitted real-case quality evaluation remain necessary. No historical processing, AI expense, tenant-wide rollout, merge or production deployment is authorized by this draft. The feature must remain off and this PR must remain on hold.

The CI workflow runs seven mandatory erasure release tests after the other tests. The original three contact tests remain red (including SQLSTATE 55P03), two source tests expose an in-flight RR quarantine race and replay of a deleted source without an existing fact, a cross-channel test exposes in-flight source context after contact erasure, and the local transport test demonstrates transmission starting after a deletion request arrived. See `customer-memory-pending-erasure.md` for the incomplete pending implementation and recovery boundaries. A separate synthetic test injects a transaction failure, checks rollback of contact, link, fact, versions, suppressions and fences, then executes an explicit SQL retry. This does not establish automatic retry by any real CRM deletion client.

The checked-in contact trigger's nonblocking channel lock is deliberately kept visible as a failed design, not a proposed release fix. A blocking channel lock was tested and reverted because a single SQL transaction can delete contacts in different channels in an order the row trigger cannot control. The repository's known CRM contact action archives contacts; the complete set of physical-delete, cascade and external SQL consumers is not established. A replacement must handle their existing transaction boundaries without changing successful deletion into an unhandled error. An alias-history graph alone does not make already prepared contexts safe: identity mutation, erasure and external model dispatch still need an atomic authorization/revocation boundary. Any persistent HMAC alias graph is sensitive pseudonymous metadata and requires atomic identity-writer coverage, key handling, incomplete-history fail-closed behavior and retention policy; PostgreSQL triggers do not possess the existing application HMAC key.
