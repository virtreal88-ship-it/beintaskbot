# Customer Memory: audit and implementation boundary

Audit base: `fc75c2899b7b86de42bf2cafdbdd116e9717d821` (2026-11-03). This is a code audit of selected paths, not a production or data-quality audit. This first slice is dormant: it does not install tables, expose APIs, call AI, change agent contexts, or enable campaigns.

## Existing mechanisms and limits

| Concern | Existing code | Implication for memory |
| --- | --- | --- |
| CRM subjects | `tenant_crm_native_schema.py` has tenant-scoped native contacts and companies, with a mutable contact-to-company link. | Use the existing entity IDs; do not infer that a contact's preference belongs to their company. An object/store subject is not established by this audit. Do not invent one from a name. |
| WhatsApp routes | `tenant_connect_direct_identity.py` stores provider aliases per tenant and Connect channel and refuses conflicting route merges. `tenant_connect_owner_identity.py` stores owner assertions and revocations for a pair in one channel. | A provider alias identifies a route, not a permanent human identity across channels. Group routes must not resolve to individual people. Revocation and disputes must invalidate any derived projection. |
| CRM contact mapping | `tenant_crm_native_contacts.py` first uses tenant-scoped phone identity; absent that it selects the first active contact matching the phone, then updates a route's `contact_id` on conflict. | This is operational linkage, not sufficient evidence for historical personal memory: duplicate numbers, reassignment, and prior ownership changes are not resolved here. Do not infer a confirmed person or reuse all linked histories merely from this mapping. |
| External IDs | `tenant_crm_identity.py` / `tenant_crm_identity_schema.py` prevent conflicting internal/external mappings within tenant, provider and entity type. | Reuse for provider correspondence, but a mapping is not proof of who authored each statement or owned a phone over time. |
| Access | `tenant_operator_access.py` rechecks active membership and policy; `assert_route` checks a concrete route and applies deal visibility for Kommo. `tenant_case_source_inventory.py` has tighter owner and case/source checks for its own purpose. | Access must be recomputed for each actual source and principal before any projection; do not assume a CRM or route grant implies access to all linked sources. No generic agent-level source ACL suitable for every memory reader has been demonstrated. Fail closed for unsupported source/principal combinations. |
| Agent identity | `tenant_dialog_ai_context.py` and `tenant_operator_case_submission.py` bind the assigned agent and revision. | Memory must be additional context only after these gates, and must not weaken them. Validate the assignment again where the existing execution requires it. |
| Current evidence | `tenant_support_case_context.py` bounds selections and fingerprints messages and saved media evidence; `tenant_ai_agent_worker.py` enforces current media coverage in applicable paths. | Old memory cannot substitute for current case evidence. Reuse saved analysis only with its source/version; missing media is unknown. |
| Costs and campaigns | `tenant_ai_spend_budget.py` reserves spend and distinguishes `unknown`; `tenant_knowledge_campaigns.py` has bounded fragments, stop states and unknown-outcome fencing. | Reuse primitives, but do not publish customer memory as knowledge or make a knowledge campaign silently run memory extraction. Build/update costs need distinct operation attribution; response tokens stay in the existing run. |
| Language | `tenant_summary_language.py` owns the company language policy and uses AZ as legacy fallback; it does not rewrite historical source text. | Reuse the policy and customer evidence; distinguish a customer's preference from the language of the current message. |

## Required integration design

* Keep subjects separate: native contact, native company, and a real existing object when a suitable entity is established. A group or case can retain facts in its own scope without attributing them to an unverified organization or person. Record the message author independently from the subject.
* Persist source references and temporal fields separately from facts: event time, observation time, validity interval, last confirmation, provenance kind and reliability. An AI proposal starts as requiring review; repeating it does not establish a cause or confirmation. Case status, assignee and next action are read from the current case/task, not maintained as a competing registry.
* Source and subject membership must be revalidated on read, and identity link changes, source access revocation, edits and deletion must fence in-flight work and derived contexts. The present mapping lacks a complete versioned history and reassignment workflow. Until a trustworthy binding and invalidation boundary exist, do not expose cross-dialog personal projections.
* Within one transaction, lock and compare memory, identity and source versions before applying work; a later AI result is stale when any changed. A deletion suppresses re-extraction from that source and subject without retaining the deleted value, and invalidates every derived representation. Keep correction and do-not-store semantics distinct. Hashing an arbitrary secret does not make a tombstone safe: use non-content source/subject identifiers and protect their access.
* Source ACL filtering happens before selecting facts, summary, count, search, version or export. Do not share a prebuilt all-source summary across principals. The future reader takes tenant, verified subject, conversation, assigned agent and authenticated user/service principal and returns only authorized facts, source references, freshness/version and incompleteness. It distinguishes no memory, ambiguous identity, denial and temporary error. Reading never launches a build or AI call. Never return existence metadata from inaccessible sources.
* Memory text is untrusted evidence, not instructions. Use an independent bounded read timeout and context budget. Fail open only for a memory outage, retaining all existing identity, access, assignment and mandatory current-media gates. Do not include secrets or raw conversation history in memory, logs, tombstones or external prompts.
* Feature flag defaults off per tenant. Backfill is independently disabled and requires an explicit, bounded grant. Use existing budget reservations, limits, source fingerprints, checkpoints and unknown-outcome fencing; do not run on deployment or analyze media again. Batch delayed messages and revisit a source when saved transcription evidence arrives. No private Copilot conversations as sources.

## Delivery and verification gates

The standalone policy in this slice only classifies potential automatic writes. It does not enforce locks, ACL, redaction, deletion, or identity checks. It must not be connected until the transaction and authorization boundaries above exist. Five offline unit tests exercise this decision table; they are not evidence of factual quality or PostgreSQL concurrency.

Next: implement durable source/subject bindings and invalidation with real PostgreSQL race tests; additive fact storage and audited manual management; principal-scoped reads; then AI integration and event/batch updates. Separately verify HTTP, desktop/mobile UI, existing agent/media gates, exact-head CI and independent review. Measure baseline latency before proposing a timeout; the proposed 1,000–1,500 tokens and 10–20 clients are not approved limits. A paid real-data pilot, mass backfill and tenant-wide rollout need their own authorization. No production rollout is implied by this audit.

## Manual direct-route prototype

A disabled server-side slice now stores manually entered facts for native CRM contacts and exact text messages in explicitly owner-confirmed direct Connect routes. It does not use a phone match as evidence and does not write or replace CRM identity mappings. An assertion can be revoked; it is unique per active route and facts tied to the old assertion are excluded from reads. Each fact read rechecks the active tenant member, current existing customer and dialog permissions, exact route, identity conflict state and the source message fingerprint, including the PostgreSQL row revision. The row revision is a conservative prototype fence, not a durable identity/source event history; transaction ID wrap, restores, link revocation and source-writer integration still require a reviewed production design. There is no shared summary, cache, search, agent access, extractor or automatic update. Unsupported/group subjects and media sources are closed.

Both `CUSTOMER_MEMORY_ENABLED=1` and a tenant workflow policy `customer_memory` containing exactly `{"enabled":true}` are necessary; neither is turned on by this PR and there is no activation endpoint. Manual edits compare versions under PostgreSQL locks, and deletion removes the fact and its value history and records only source/contact identifiers for suppression. Audit entries contain event metadata, not values. A conservative text filter rejects recognizable credential and payment patterns; it cannot prove arbitrary free text is secret-free. The feature must remain disabled until a stronger reviewed handling strategy is in place.

The HTTP interface is a developer-facing foundation, not a complete user flow: there is no customer-card UI, no way to select an evidence message from the interface, and no authorized general service-principal/agent adapter. An owner can delete a known fact even after its source or link becomes unavailable, but a complete subject-wide personal-data erasure flow is not implemented. The prototype does not implement identity-change hooks/in-flight fencing across all existing writers, and only supports native contacts and direct Connect text. It currently allows at most one fact per contact/message to prevent an equivalent duplicate surviving deletion; multiple independent facts from one message need a reviewed per-fact suppression design. These are release blockers, not product features. It cannot be merged or deployed as a completed memory system. Tests on disposable PostgreSQL and HTTP do not establish extraction quality, broader permissions or browser behavior. Independent review and exact-head checks are still required.
