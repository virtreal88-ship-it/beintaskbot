## 1. Что выяснено именно по существующему `/webapp`

### Адреса и авторизация

`legacy_runtime_config.py:18–20` использует `KOMMO_TOKEN` из среды сервера и задаёт `example.kommo.com`. Основной webapp адрес — `https://production.example.invalid/webapp`. Токен в локальной сессии отсутствует; production-секрет не извлекался.

Открыта действующая страница `/webapp` в доступном браузере. Она требует авторизацию через Telegram и не показывает чаты до входа. Это ограничение текущей сессии проверки, а не свидетельство, что действующий webapp не работает. Для дальнейшего чтения каналов и диагностики нужен обычный вход владельца в открытую вкладку. Обход авторизации и подстановка сотрудника не выполнялись.

### Отправка

`bot.py:13345`, `handle_api_deal_chat_send` проверяет пользователя и сделку, определяет talk/chat канала и передаёт отправку серверному сервису. `bot.py:8853`, `_post_kommo_json` использует серверные `HEADERS` и `_http.post`; не получает cookie Kommo из браузера сотрудника.

В `legacy_kommo_chat_sender.py` обычный текст без цитирования отправляется через **официальный** `POST /api/v4/talks/{talk_id}/send_message`. Значит, использовать тот же внешний транспорт в фоновом worker архитектурно возможно. Ваше сообщение о работающей отправке в webapp — полезное эксплуатационное свидетельство; в этой сессии фактический POST и delivery_status не проверены.

Цитирование и часть голосовых сценариев имеют запасные `ajax`/`amojo` endpoints и несколько попыток. В sender при исключении возможен переход к следующей попытке. **Этот fallback-код не использовать как доказательство гарантированной официальной совместимости и не переносить целиком в автономный AI.** Для обычного AI-текста уже есть более подходящий `tenant_chat_send_provider.py`: один официальный POST, ID принятия и запрет слепого повторения при неизвестном результате.

### Чтение и каналы

`legacy_kommo_chat_reader.py` начинает с официальной истории talks, но содержит внутренние fallback-маршруты. Успешно показанная история в UI сама по себе не доказывает, что именно официальный history endpoint доступен действующему токену. Это нужно подтвердить отдельно.

`bot.py:17193`, endpoint `/api/admin/integrations`, описывает WhatsApp через Kommo и Instagram через Kommo, а прямой WhatsApp Business/WABA как отключённый. Комментарий указывает на действующую «grey Kommo connection». Эти записи формируются кодом, а не запросом всех установленных виджетов: это **не полный актуальный inventory провайдеров** и не доказательство Wappi либо другого конкретного поставщика. Поддержка Facebook/TikTok/Telegram в классификаторе также не означает их фактическое подключение.

Legacy-классификатор может трактовать неизвестный origin как WhatsApp. Для AI это неприемлемая эвристика: при неустановленном источнике блокировать отправку. Два WhatsApp-подключения необходимо различать по внешнему source/origin/chat, не только по названию канала.

### Входящие без браузера

В `bot.py:5648` есть серверный `/webhook/kommo` для входящих. Он существует независимо от `/webapp` и обновляет legacy inbox/cache/pulse. Но из кода нельзя установить, подписан ли он сейчас в Kommo, какие события доходят и какова задержка. Обработчик не создаёт durable AI jobs для SaaS и отвечает 200 даже при исключении. Эти свойства нельзя переносить в новую подтверждаемую цепочку.

Вывод: переиспользуем серверные механизмы и официальные endpoints; не запускаем новый AI через browser refresh. Не меняем legacy webhook и sender до получения отдельного технического основания.

## 2. Два официальных пути отправки

### Путь 1 — прямой Chats API add-on

Возможность работы с чужими интеграциями сообщений официально предусмотрена, но отличается от Chats API для собственного канала. Нужны OAuth scopes `External chat history` и `Sending to external chats`. Это не требует нашей собственной WhatsApp/Instagram-интеграции. [Chats API add-on](https://developers.kommo.com/reference/chats-api-add-on)

История: `GET /api/v4/talks/{talk_id}/messages`, page/limit до 250, фильтр created_at. Возвращаются direction, message ID, chat ID, origin, автор, тип вложения, ссылка и delivery_status. Права авторизовавшего пользователя ограничивают видимость. Ссылка на файл ещё не гарантирует доступность его содержимого. [История разговора](https://developers.kommo.com/reference/get-conversation-messages)

Отправка: `POST /api/v4/talks/{talk_id}/send_message`, текст и/или attachment. HTTP 202 возвращает ID принятого сообщения; это не подтверждение доставки. Ошибки включают 402 — тариф/квота/подписка, 403 — scope, 404 — talk, 422 — закрытый разговор. В опубликованном контракте нет клиентского idempotency key для этой операции; exactly-once не подтверждено. [Отправка](https://developers.kommo.com/reference/send-message-to-conversation)

Scopes действующего legacy-токена и SaaS OAuth могут различаться. Если интеграция запросила новые права, уже установленным пользователям требуется повторная выдача доступа. Не менять права или переподключать production автоматически. [OAuth permissions](https://developers.kommo.com/docs/permissions)

### Путь 2 — собственный Salesbot-блок

Kommo документирует server-side `widget_request`: бот передаёт запрос на наш HTTPS endpoint, ожидает 200 до двух секунд; затем сервер продолжает конкретный запуск через `return_url` с `execute_handlers/show`. Запрос содержит JWT; предусмотрена проверка с секретом интеграции. Другой запущенный бот для той же entity может препятствовать продолжению. Это автономный механизм, но требует собственного блока/flow и контроля конкуренции. [Руководство Salesbot](https://developers.kommo.com/docs/private-chatbot-integration)

Публичное руководство не подтверждает, что Salesbot-отправка расходует тот же пакет Chats API, и не является обещанием бесплатной отправки. До проверки тарифа и правил Billing учитывать этот путь как альтернативу, а не способ гарантированно обойти расходы. История внешних каналов и доступ к вложениям остаются отдельной проверкой. Не запускать действующий KWID Salesbot как зависимость нашей системы.

Предпочтение: если обычные сообщения `/webapp` действительно идут через официальный send endpoint и тариф/scopes это разрешают, расширить уже работающий путь. Salesbot вводить только при доказанной необходимости.

## 3. Серверный приём и резервное обнаружение

General webhook поддерживает `add_message`, `add_outgoing_message`, `add_talk`, изменения сделки. Это позволяет получать входящие и выявлять ответ менеджера без присутствия UI. [Список событий](https://developers.kommo.com/reference/webhook-events)

General webhooks через API доступны на Advanced/Pro/Enterprise. Payload документирован как form-urlencoded. Ответ нужен за две секунды; неудачные доставки повторяются, а серия ошибок может отключить подписку. Новый ingress должен сохранять сигнал до успешного ACK, затем проверять сообщение через tenant OAuth. Не переносить HMAC/JWT собственного Chats API или Salesbot на general webhook: это разные протоколы. [General webhooks](https://developers.kommo.com/docs/webhooks-general)

Для новых разговоров есть официальный `GET /api/v4/talks`: pagination до 250, chat/source/account ID, origin, статусы, фильтры entity/contact/talk и only_in_work. Документированный updated_at в ответе не означает наличие фильтра updated_at: его нет в опубликованном списке параметров. Поэтому нельзя обещать дешёвую инкрементальную сверку всех чатов только по этому полю. [Список conversations](https://developers.kommo.com/reference/get-talks)

Более экономный кандидат для reconciliation: `GET /api/v4/events` с фильтрами created_at и type, cursor с временным перекрытием и локальной дедупликацией; события определяют изменившиеся entity, а содержимое сверяется через историю. Полноту, retention и привязку event к правильному talk проверить на аккаунте, не считать events заменой истории. [Events list](https://developers.kommo.com/reference/events-list), [типы events](https://developers.kommo.com/reference/events-types)

Ограничение REST — не более семи запросов в секунду; превышение даёт 429, систематические нарушения могут привести к блокировке IP. До 100 webhook-подписок на аккаунт. Существующая система уже использует pacing; новую сверку включать в общий бюджет запросов вместе с CRM и legacy. [API limitations](https://developers.kommo.com/docs/limitations)

После перезапуска обрабатываются сохранённые события; при недоступном ingress нужна сверка, а не только надежда на webhook retry. `railway.toml` запускает `bot.py`, задаёт `/health` и restart always, но не доказывает настройки sleep/реплик и состояние production worker. Их проверить отдельно.

## 4. Тариф и возможные расходы

### Kommo Chats API

Коммерческая страница: Base/Advanced — без Chats API пакетов; Pro — 500 исходящих/месяц **на аккаунт**; Enterprise — индивидуальные условия. Trial — 100 до окончания trial; Pro-plan trial имеет отдельное ограничение. Входящие и история не расходуют пакет. Дополнительные пакеты: **3 000 — $10; 10 000 — $20; 50 000 — $75**. Включённые сообщения не переносятся; купленные действуют до конца подписки. При прекращении подписки остаток блокируется с правилами восстановления. [Billing Chats API](https://support.kommo.com/docs/chats-api)

Есть расхождение: API reference отправки указывает 500 для Pro/Enterprise, коммерческая страница — Enterprise custom. Для вашего аккаунта окончательны отображаемые условия Billing и письменное подтверждение Kommo, если данные расходятся. Не обещать одинаковый Enterprise пакет.

Одна успешно отправленная реплика расходует одну единицу, а не один диалог. 300 ответов/месяц на чат из ТЗ не означает 300 сообщений на весь аккаунт. Ручной `/webapp`, наша автоотправка и другие интеграции через этот API могут использовать общий пакет.

### Возможный переход тарифа

Текущая публичная страница указывает Base $25, Advanced $35, Pro $45 за пользователя в месяц; Enterprise custom. Это витринные условия, а не доказательство вашего действующего legacy-тарифа, скидки, валюты или стоимости апгрейда посреди оплаченного периода. [Kommo pricing](https://www.kommo.com/pricing/)

Цена «в месяц» не означает возможность помесячной оплаты: публичная страница указывает минимальную подписку шесть месяцев. Существующая оплата и условия изменения вашего тарифа пока не просмотрены. Возможные экономия/доплата при понижении рассчитываются по Billing, а не только умножением витринной разницы.

Сценарный расчёт: если потребуется Advanced → Pro по этим ценам, увеличение составляет $10 × число оплачиваемых пользователей в месяц. Для пяти пользователей это $50/месяц до расходов модели и канала — больше заявленных $45 KWID. Если действующий тариф уже обеспечивает официальный API, этой прибавки может не быть. Сначала проверить Billing; тариф не менять.

### Модель и hosting

Дополнительные расходы: текстовые input/output tokens, embeddings при необходимости, транскрипция входящего аудио, vision изображений, тестовые генерации, хранение файлов/журналов и постоянно работающий backend. Фактическая сумма зависит от выбранной модели, объёма истории и медиаматериалов; фиксированного тарифа «за AI-агента» у нашей реализации не предполагается. На этапе A модели не подключались и платные запросы не выполнялись.

Месячная экономия оценивается так: **$45 KWID − прирост тарифа Kommo − новые Chats API пакеты − прирост расходов канала − расходы AI − прирост hosting**. Уже оплачиваемые неизменные расходы не вычитать повторно. Это сравнительная формула, не гарантия экономии. Требуются реальные объёмы исходящих по аккаунту и usage модели на контрольных примерах; тест модели относится к следующим согласуемым этапам.

Пример лишь ёмкости: Pro с нетронутыми 500 включёнными сообщениями и пакетом 3 000 даёт 3 500 доступных отправок; нельзя считать $10 постоянной месячной платой или бесконечно переносимым остатком.

## 5. Что ещё нужно доказать для закрытия этапа A

1. После входа в открытый `/webapp` прочитать существующую диагностику и доступные каналы. Не считать hardcoded «connected» доказательством разрешений API.
2. В аккаунте `example.kommo.com` проверить текущий тариф, Chats API Usage/Add-ons, число лицензий и фактические коннекторы/номера. Если интерфейс webapp этого не показывает, требуется вход в сам Kommo, а не новый секрет в чате.
3. Проверить именно SaaS OAuth интеграцию отдельно от `KOMMO_TOKEN`: официальная история нужных talks, файл/аудио, возможности read-only events/talk discovery и scopes. Не обновлять права автоматически.
4. Проверить существующую webhook-подписку и журналы входящих при закрытых `/app` и `/webapp`. Событие должно содержать достаточную идентичность; сохранить время получения, direction, origin/source, talk/chat и результат подтверждения через API.
5. Для каждого реально используемого канала получить один проверяемый набор входящих, включая новый разговор, и установить доступность точного исходящего маршрута. Сейчас по документации статус «возможно при выполнении условий», а не «проверено на аккаунте».
6. Отправку проверить только по отдельному разрешению в конкретный тестовый чат: один обычный текстовый POST, ID принятия, затем доставка/история. Дополнительные адресаты и повтор после timeout не допускаются. Отказавший канал не заменяется автоматически другим.
7. Если официальная история/отправка недоступны — выяснить причину по статусу и Billing, затем выбрать минимальный рабочий путь. Не восстанавливать старые внутренние endpoints как обход ограничений.
8. После доказательства канала выполнить оставшуюся часть A: disabled-by-default durable ingress, очередь, reconciliation и mock-тесты. Прежде не выбирать окончательный transport на основании предположения о тарифе.

## Вывод

Ваше указание проверить `/webapp` позволило установить действующий серверный путь, аккаунт и используемую в коде схему каналов. **Обычный текст в `/webapp` уже использует тот официальный API, который подходит фоновому AI.** Не требуется писать собственный мессенджер.

Осталось подтвердить живые права, тариф, поставщика WhatsApp, доступность history и доставку по каждому каналу. Сейчас доступ к `/webapp` в инструментальной сессии остановился на Telegram-входе. Это конкретное препятствие для live-проверки, а не завершённый отрицательный результат. До устранения этого препятствия этап A считается незавершённым; переход к другим этапам запрещён вашим текущим указанием.
