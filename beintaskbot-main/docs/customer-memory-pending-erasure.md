# Customer Memory: pending erasure foundation — HOLD

The owner confirmed that a deletion request must immediately prevent new uses of the affected fact and can remain in progress while earlier operations are safely stopped or completed. A previously admitted operation is **not** authorized to start a new transmission after the deletion request. Already transmitted bytes cannot be recalled by this system.

This draft implements only an owner-only, manual fact-erasure foundation. A successful transaction removes the selected fact group and its version values, writes source/group/subject fences, reserves the erased fact IDs and records a non-content `pending` request with a deterministic retry ID. A retry of the same tenant/contact/fact/version returns the saved status even when the fact is already gone. A current authorized owner can page through non-content request statuses, or query a known request ID, even if the memory process or tenant feature switch is off. Active membership and customer deletion/dialog permissions remain required. The owner can query a known request after physical contact deletion while the tenant remains accessible; after tenant deletion, the old owner cannot pass the current membership guard.

The request coordinator and erased fact IDs intentionally have no contact/tenant cascade FK. They contain UUIDs, actor ID and timestamps, not fact values or source text. These identifiers and HMAC source tokens are **pseudonymous personal metadata**, not anonymous data. Retention, key rotation, backup restoration, tenant-incarnation and authorized administrative recovery policies are not settled. No automatic TTL or unsafe cleanup is implemented.

While an erasure is pending, this draft hides all memory of the affected contact and rejects new writes for that contact, including independently-worded or newer evidence; this is conservative because it cannot prove semantic non-equivalence without retaining the erased value. A tenant-wide, short PostgreSQL source gate orders *manual fact erasure* against supported current-version source reads/writes across contacts and mixed HMAC key generations. Memory operations fail closed on unsupported transaction isolation or a busy gate. A deletion transaction may wait at most two seconds for a lock; on timeout the transaction rolls back and **no request has been accepted**. The owner must retry. This is not the desired nonblocking durable admission and needs a reviewed asynchronous coordinator.

The owner UI displays `Deletion in progress`, persists it through reload and pages through status records without showing the erased fact. It states that original messages are not deleted. When status is unavailable, the UI shows an error rather than treating it as completion. The status API remains available to the current owner after a contact is physically deleted, but the current contacts UI requires a live contact card and cannot show such a request after the card disappears; a separate owner recovery view is still needed. After tenant removal there is deliberately no fallback based on caller-provided UUIDs or a former role. Ownership transfer and current tenant permissions are rechecked.

**There is no completion path yet.** No pending request may become `completed` until a reviewed, crash-safe coordinator proves that all relevant in-flight readers, workers and controlled transports have finished or are fenced and that required local derivatives have been removed. The current implementation does not control external AI transport, already materialized contexts, direct SQL, tenant cascade, or old application binaries. It does not guarantee that a source-derived duplicate under another subject is physically purged; the global source fence hides it but retained rows need reviewed provenance-aware removal. Previously transmitted provider data cannot be recalled. Do not infer deletion at the provider or factual quality from this draft.

Source erasure events contain domain-separated HMACs for both channel+external ID and tenant+external ID. This closes tested sequential same-source replay after reassigning a contact or changing channel. Empty legacy HMACs or mismatched key generations cause a broad tenant memory quarantine. A source DELETE in `REPEATABLE READ`/`SERIALIZABLE` also records a content-free tenant sentinel because its snapshot can miss recently committed facts. There is no reviewed recovery for such quarantine, and the source-trigger sentinel does **not** fence a reader that already passed its check. A source deleted before any memory fact existed can still be replayed. Both are explicit failing release tests. Source-trigger compatibility, accumulation of pseudonymous events, older binary rollback and mixed deployments are not established.

The isolated test-only event receipt/checkpoint prototype is not connected to CRM, workers, AI, or this deletion path. It uses synthetic data and no paid calls. The three pre-existing contact erasure tests, two source erasure tests, one cross-channel in-flight contact/source test and one transport-start test remain mandatory red release gates. The feature is off by default, but a flag alone does not make an already installed trigger safe; **do not merge, deploy or activate this branch** until the gates, independent review, source/identity/tenant/transport fencing, retention policy, and real case quality evaluation are complete.

The test-only local transport experiment in `tests/customer_memory_local_transport_prototype.py` serializes a synthetic localhost socket write and a pending transition with one in-process mutex, after closing its PostgreSQL transaction. It orders a start against the *commit* of pending within that coordinator and includes a separate-process read of persisted pending. It does **not** satisfy the owner's stricter boundary: a sender can hold the mutex before writing, a deletion request can then arrive, and the write can start while that request waits. This is an explicit failing release test. Two independent coordinators also allow a stale POST after pending. This is not distributed fencing, a production transport, proof of crash safety or a way to recall bytes; its mutex has no fairness guarantee. No external provider or customer payload is used.

The memory recovery functions do not call schema migration. Authentication can still invoke the existing shared platform migration; in the new code it skips the memory slice when the process flag is off, but may run other DDL. A fresh synthetic database and real signed SID authentication exercise this path. Existing triggers are not removed when switched off; old binaries may still install them. If the coordinator exists only partially, recovery fails closed. A process starting OFF caches platform schema readiness; enabling requires new processes and an explicit schema-readiness check, not an environment change in a running process. These details do not make mixed-version or partially migrated deployments safe.

The source/contact triggers now point to versioned `*_v2` functions; an older audited binary that only replaces the old function names and creates triggers when absent cannot silently restore those two old trigger bodies. Cold startup checks the binding and avoids replacing an already-correct trigger. Synthetic tests cover old-to-v2 binding and this no-op under conflicting table locks. This is **not** safe mixed-version rollout: old readers/writers still do not understand pending, the new HMAC/source fences or fact-ID reservations; all such processes and queues must be fenced before activation or rollback. The actual migration on first upgrade still needs DDL locking and a measured rollout plan.
