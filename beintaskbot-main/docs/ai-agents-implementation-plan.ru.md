# План замены GPT Agent от KWID внутри Beintaskbot `/app`

Дата исследования: 12 октября 2026. Статус: технический план для согласования; реализация не начата.

Редакция 2: учтено новое ТЗ «AI Agents — замена GPT Agent AI внутри Beintaskbot SaaS». Оно уточняет обязательную обработку аудио/изображений, инструкции этапов, задержку 40 секунд, лимиты на чат и CRM-триггеры. При расхождении с первоначальным планом применяются требования этой редакции.

Авторизован только этап A. Промежуточная проверка возможностей, legacy `/webapp`, тарифов и ограничений вынесена в [отчёт этапа A](ai-agents-stage-a-kommo-feasibility.ru.md). Есть уточнение к предыдущей оценке: коммерческая документация указывает индивидуальные лимиты Enterprise, несмотря на 500 в API reference. Фактический аккаунт и Billing ещё требуют live-проверки; этап A не завершён. Следующие этапы требуют нового подтверждения пользователя.

Владелец подтвердил действующий Pro для `example.kommo.com`. Предварительно апгрейд для выбранного прямого пути не нужен. Понижение на Advanced/Base до проверки альтернативного пути может отключить нужный Chats API; доступность обычных мессенджеров на Base не доказывает доступ внешнего AI. Billing и live scopes пока недоступны в инструментальном браузере без входа.

## 1. Решение и главный критерий

Создать модуль **AI Agents** в существующем `/app`, используя backend проекта, PostgreSQL, авторизацию, шифрование ключей, CRM-команды и текущий UI. Существующий Chat AI сохранить.

**AI должен принимать и обрабатывать новое сообщение при закрытом `/app` у всех сотрудников.** Для этого получение событий, очередь, генерация и отправка работают на сервере. Браузер используется для настройки и контроля.

Первым результатом разработки должна быть проверенная цепочка входящих событий без участия браузера. Красивый интерфейс и ручные черновики сами по себе не доказывают возможность замены KWID.

Три принципа реализации: минимальное расширение существующих сервисов; проверка сначала в тестовой компании и Manual с выключенными внешними действиями; независимые CRM и Messaging adapters для будущего BeinSystems и других источников. Не создавать новый UI-фреймворк, новый AI-сервис, отдельную векторную БД или полноценный SaaS-биллинг. Нулевой риск нельзя гарантировать заранее: изменения ограничиваются флагами, совместимыми миграциями, регрессионными проверками и возможностью отключить модуль без удаления данных.

Закрытые настройки KWID, ваши действующие сценарии и фактические права OAuth нужно сверить перед пилотом.

## 4. Что уже есть в проекте

1. **Chat AI:** `tenant_chat_ai_api/service/store/settings/provider/policy/schema.py`. Есть авторизованные ручные запросы, черновики, резюме и транскрипция, зашифрованный ключ компании, резервирование вызовов и дневной лимит их количества. Сейчас инструкция фиксированная, нет настраиваемых независимых агентов и базы знаний. Провайдер возвращает текст; полноценный учёт денежных расходов и токенов нужно добавить.
2. **История:** `tenant_chat_reader.py` читает talks и сообщения через Kommo API; `tenant_chat_sync.py` нормализует и сохраняет их. Чтение ограничено шестью talks и четырьмя страницами по 250 сообщений; превышение завершает чтение ошибкой. Для автономной обработки требуется отдельный инкрементальный механизм, а не снятие ограничений и загрузка всей истории при каждом сообщении.
3. **Отправка:** `tenant_chat_send_*` проверяют права и маршрут, сохраняют durable receipts, различают `accepted`, `unknown`, `blocked` и не повторяют неизвестную отправку. Этот механизм полезен, но ориентирован на сотрудника и сделку, а не на сервисного агента и конкретный чат.
4. **CRM:** есть tenant repository, policy, команды задач, согласования и provider-neutral `tenant_crm_provider.py`. Слой провайдеров уже начат; создавать параллельную CRM-архитектуру не требуется.
5. **BeinSystems:** уже есть конфигурация, шифрование и CRM-адаптер. Публичные capabilities этой интеграции в коде указывают `chats=False`, `webhooks=False`. Это не готовый канал входящих сообщений.
6. **Фоновые процессы:** `bot.py` регистрирует CRM worker каждые 15 секунд. Он обрабатывает сохранённые задания `leads`/`tasks`; это не периодическое чтение новых сообщений во всех чатах.
7. **UI:** `/app` отдаёт `docs/tenant-app.html`; поведение дополнено `docs/tenant-*.js` и компонентами React/Chakra из `ui/src/main.jsx`. Новый раздел должен встроиться в эту композицию.

## 5. Проверка входящих сообщений: обнаруженный разрыв

### Текущая цепочка SaaS

Открытие чата вызывает `loadChat(..., refresh=true)` → `/api/platform/crm/chat?lead_id=...&refresh=1` → `tenant_chat_api.py` → `_sync_tenant_chat` → чтение Kommo → SaaS-кэш.

Ручной AI вызывается отдельным POST `/api/platform/chat/ai` с авторизацией сотрудника. Само появление сообщения в кэше не ставит задачу автоматического ответа.

### Текущий webhook

`bot.py:handle_kommo_webhook` принимает входящие независимо от браузера. Но обследованный обработчик обновляет legacy-кэши, inbox, pulse и уведомления, использует глобальные идентификаторы/состояние и не вызывает SaaS AI Agents. В нём нет достаточной цепочки `account → tenant → durable incoming event → autonomous AI job`.

Обработчик отвечает HTTP 200 даже при исключении. Переносить это поведение на новую очередь нельзя: иначе провайдер считает потерянное событие принятым.

Есть таблица `saas_tenant_webhook_events` с `tenant_id`, `fingerprint`, временем получения, но поиск в Python-коде обнаружил только её объявление. Это заготовка дедупликации, не работающая очередь AI.

**Вывод:** существующий backend умеет получать некоторые входящие без открытой страницы, однако автономный AI для `/app` сейчас не обеспечен исследованной цепочкой. Простое добавление кнопки или вызова генерации после браузерного refresh проблему не решит.

## 6. Как получать сообщения независимо от `/app`

### Основной вариант: general webhooks Kommo

Использовать `add_message` и `add_outgoing_message`; события изменения сделки/этапа и talk применять для актуализации состояния. Названия событий подтверждены [официальным списком](https://developers.kommo.com/reference/webhook-events).

Создать отдельный SaaS endpoint, предварительно `/api/platform/integrations/kommo/events/{connection_token}`. Token случайный, привязан к версии подключения и не содержит открытый tenant ID. Tenant определяется доверенной записью подключения; данные аккаунта из payload сверяются с этой записью. Поддержать реальные JSON и form-urlencoded payload, несколько событий за запрос и неоднозначные/неполные данные.

Способ подтверждения подлинности general webhook проверить отдельно: не предполагать, что у него есть HMAC из Chats API. При отсутствии документированной подписи использовать секрет callback, ограничения запроса и подтверждение принадлежности сообщения через tenant OAuth до каких-либо действий. Секрет пути скрывать в логах и регулярно заменять при переподключении.

Endpoint выполняет только быструю проверку и транзакционное сохранение. Нормализация, загрузка истории и AI работают позже. Отвечать 2xx после commit; при недоступной БД возвращать ошибку. Kommo ожидает ответ в пределах двух секунд, повторяет неудачные доставки и может отключить webhook после серии ошибок. Поэтому нужны мониторинг подписки и резервная сверка. [Правила webhook](https://developers.kommo.com/docs/webhooks-general)

### История и отправка

В текущем проекте уже используются официальные endpoints `GET /api/v4/talks/{talk_id}/messages` и `POST /api/v4/talks/{talk_id}/send_message`. Первый требует `External chat history`, второй — `Sending to external chats`. [История](https://developers.kommo.com/reference/get-conversation-messages), [отправка](https://developers.kommo.com/reference/send-message-to-conversation).

Доступность зависит от тарифа. Для Chats API add-on документация перечисляет Trial, Pro, Enterprise, Partner и Technical; general webhooks через API имеют собственные условия. Нельзя считать наличие обычного OAuth достаточным. [Chats API add-on](https://developers.kommo.com/reference/chats-api-add-on)

Первый этап должен подтвердить для вашего аккаунта: тариф, scopes, чтение нужного внешнего канала, приём incoming/outgoing и возможность отправки. Прямая отправка расходует лимиты Kommo; документация указывает 500 включённых запросов в месяц для Pro/Enterprise с возможностью покупки дополнительных. Устранение $45 KWID не означает нулевые расходы. [Ограничения отправки](https://developers.kommo.com/reference/send-message-to-conversation)

Если прямая отправка недоступна, отдельно оценить собственный Salesbot-адаптер по [официальному руководству Kommo](https://developers.kommo.com/docs/private-chatbot-integration). Он не должен зависеть от KWID. Это альтернативный путь со своими проверками и состоянием выполнения; нельзя молча переключаться на другой канал или обещать совместимость до проверки. Собственный Chats API канал также не даёт автоматически доступ к каналам чужих интеграций.

### Резервное серверное чтение

Планировщик обходит подключения с включёнными агентами, обнаруживает разговоры, включая новые и не открывавшиеся сотрудниками, и дочитывает сообщения с сохранёнными cursor/watermark и перекрытием временного окна. Не опираться только на локальные сделки или `lead.updated_at`: новое сообщение не обязано менять сделку.

Начальная целевая частота — 30–60 секунд для активных чатов и более редкий полный обход доступных разговоров; окончательные интервалы определить по объёму и API-лимитам. Проверить документированный список conversations/talks, пагинацию и обнаружение закрытых/новых разговоров. Резервный обход отправляет события в тот же inbox, с теми же ключами дедупликации. Если надёжное обнаружение новых разговоров недоступно, это ограничение блокирует обещание полной резервной доставки.

При включении агента зафиксировать `activation_at` и начальные cursors. Исторический импорт формирует контекст, но не запускает ответы старым клиентам. После простоя применить срок актуальности обращения и проверить, не ответил ли менеджер.

### Условия постоянной работы

Worker стартует с backend через существующий механизм фоновых задач, не с посещением страницы. Проверить фактический hosting: процесс не засыпает, health check отражает состояние worker, после рестарта задача поднимается снова. `Procfile` запускает `bot.py`; этого недостаточно, чтобы подтвердить настройки production. Redis/Celery и отдельный AI-сервис для первого этапа не требуются.

## 7. Внутренняя обработка одного обращения

Цепочка: **Kommo → SaaS inbox PostgreSQL → нормализованное событие → очередь чата → контекст и знания → AI → повторная проверка → draft либо отправка → журнал и расходы**.

1. Сопоставить подключение, tenant, внешний чат и внутренний conversation ID. Событие без надёжного сопоставления оставить для диагностики, не отвечать.
2. В одной транзакции записать сообщение, изменить revision чата и поставить/обновить задание. Повтор webhook и резервное чтение не создают новое обращение.
3. Выбрать одного агента по каналу, воронке, этапу и приоритету. Перекрывающиеся правила маршрутизации требуют явного приоритета; два агента не отвечают одновременно.
4. Собрать подряд пришедшие сообщения с задержкой **40 секунд от последнего нового входящего**. `due_at` сохраняется в PostgreSQL; каждое новое подтверждённое сообщение переносит его, повтор события — нет. Не вводить скрытый меньший интервал или максимальное ожидание, меняющее это правило. Значение настраиваемое.
5. Получить lease задания и fencing token; только один исполнитель имеет право генерировать и завершать ответ. Продлевать lease во время AI-вызова. После потери worker не запускать вторую генерацию, пока прежний вызов не завершён либо не истёк документированный максимальный срок с безопасной отменой. Fencing защищает запись/отправку, но сам по себе не прекращает уже запущенный платный вызов. Не держать длительную транзакцию во время запроса модели.
6. Проверить tenant, agent mode, grant, handoff, актуальное подключение, разрешённый этап, отсутствие человеческого ответа и бюджет.
7. Получить ограниченное контекстное окно именно данного чата и релевантные активные материалы; учесть обрезанную историю и недоступные вложения. Истории разных каналов не смешивать автоматически.
8. Зарезервировать верхнюю границу стоимости вызова; вызвать модель через внутренний AI-адаптер.
9. Перед каждым CRM-действием и отправкой повторно проверить revision, lease, конфигурацию, права и kill switch. При новом сообщении сгенерированный ответ отменяется/перегенерируется; при handoff сохраняется только в журнале.
10. В Manual сохранить редактируемый draft. Раздельная настройка: подготовка по входящему либо только по кнопке. При подтверждении снова проверить актуальность.
11. В Automatic отправить в **тот же conversation/talk**, который породил задание. Текущий выбор «последнего входящего по сделке» для этого недостаточен: у сделки может быть несколько каналов.
12. Записать receipt, execution, токены, оценку стоимости, ссылки на источники знаний и окончательное состояние.

## 8. Дубликаты, перезапуск и неизвестная отправка

- Ключ входящего: `(tenant_id, provider, connection_generation, external_chat_id, external_message_id, event_kind)`. Не использовать текст+время как основную идентичность и не считать Kommo ID глобальным ID системы.
- Уникальность задания/ответа относится к обработанному набору входящих и версии чата; повтор получения события не запускает новый ответ. Повтор явной ручной генерации имеет отдельный request ID.
- Задания хранят `state`, `available_at`, `lease_until`, `attempts`, `fencing_token`, `input_revision`, `config_version`. Claim через PostgreSQL, например `FOR UPDATE SKIP LOCKED`; просроченный lease безопасно восстанавливается.
- Перед внешней отправкой фиксируется `sending`. Рестарт в этом состоянии означает `unknown`, а не «попробовать снова».
- HTTP 202 и ID — принятие Kommo, не доказательство доставки клиенту. Delivery status проверяется по доступной истории/событиям.
- Timeout, неопределённый 5xx или сбой сохранения receipt после POST блокируют повторную отправку. Нужны сверка истории по подтверждённому ID/корреляции и ручное решение при неоднозначности; совпадение текста недостаточно.
- Повторять автоматически можно только операции с доказанной безопасностью: чтение, неподготовленные задания и явно отклонённые действия при подходящем коде ответа. Отдельно учитывать неопределённую стоимость вызова модели.
- Outgoing события сопоставлять с нашими receipts. Подтверждённый исходящий сотрудника приостанавливает AI; своё сообщение не запускает ответ самому себе. Неизвестное происхождение исходящего приводит к безопасной паузе и сверке.

Реалистичная гарантия: идемпотентная внутренняя обработка и отсутствие слепого повторного POST. Абсолютное «ровно один раз доставлено» невозможно обещать без поддержки идемпотентности и подтверждения доставки внешним провайдером.

Kill switch запрещает новые внешние операции после контрольной проверки. Уже переданный провайдеру запрос отозвать нельзя. Такой же предел действует при сообщении менеджера, которое ещё не дошло до нас через webhook; нужна финальная сверка истории и тест гонок, а не обещание нулевого окна гонки.

## 9. Права сервисного агента и передача человеку

Не имитировать браузерную сессию и не присваивать AI права owner. Ввести server-side principal `agent` с tenant, agent ID, выданными владельцем scopes, разрешёнными ресурсами и версией grant. Человеческие действия остаются под своей авторизацией. Расширить аудит типом actor без поддельного Telegram ID.

Это небольшое расширение действующих policy/command-контрактов, а не новая универсальная система IAM. `tenant_browser_session.py` и текущую авторизацию `/app` сохраняем.

Управление агентами: owner либо admin с явно выданным `ai_agents.manage`. Просмотр журналов, редактирование знаний, подтверждение черновиков и ручное возобновление имеют отдельные права.

Handoff сохраняет причину, ответственного и состояние `human`; повышает revision, отменяет ожидающие отправки, создаёт tenant-уведомление через существующий outbox. Просьба о менеджере, отсутствие информации, недовольство и необходимость индивидуального решения могут запускать handoff. Возобновление — явное действие сотрудника с правами. Самостоятельный ответ сотрудника также может ставить паузу.

CRM tools — фиксированные схемы с проверкой параметров, принадлежности компании, маршрута и согласований. Начать с чтения клиента/сделки, handoff и создания задачи через существующую безопасную команду. Для имени/телефона контакта и этапа сделки переиспользовать безопасные команды там, где они есть; иначе добавить узкие проверяемые команды с аудитом, preconditions и состоянием неизвестного результата. Эти действия нужны для предусмотренных новым ТЗ триггеров и не откладываются целиком за пределы первой версии. Создание контакта/сделки оставить выключенным до готовности безопасных команд и проверки дублей. Модель не получает SQL, произвольный HTTP или исполняемый код. Handoff определяет сотрудника для уведомления, но не меняет ответственного в CRM без отдельного разрешения.

## 10. Предлагаемые данные и миграции

Названия предварительные; все связи с ресурсами проверяются в пределах tenant, желательно составными FK `(tenant_id, id)`.

- `saas_ai_agents`: ID, tenant, имя, описание, enabled, mode, модель/provider, системная инструкция, язык, автоопределение языка, стиль ответа, ограничения ответа, настройки debounce, grants, config version, created/updated. Шаблон: disabled + Manual, азербайджанский, сбалансированный стиль, задержка 40 секунд. Стиль отображать через параметры, реально поддерживаемые моделью; не передавать неподдерживаемую temperature.
- `saas_ai_agent_routes`: agent, provider/channel, воронки/этапы, приоритет и правила выбора.
- `saas_conversations` и `saas_external_resource_mappings`: внутренние UUID, tenant, provider, generation подключения, внешние chat/talk/contact/deal ID. Внешние ID — строки; chat и talk не считать взаимозаменяемыми.
- `saas_message_events`/`saas_messaging_inbox`: исходная идентичность, направление, тип, статус нормализации, время получения, error и provenance webhook/poll. Уникальный ключ события и индексы ожидающих задач.
- `saas_ai_conversation_state`: agent assignment, AI/human/paused, last processed input, revision, ответственный, причина handoff, время активации.
- `saas_ai_jobs`: очередь с lease, fencing token, input revision, retries, due time и ключом идемпотентности.
- `saas_ai_knowledge_sources`, `saas_ai_knowledge_chunks`, `saas_ai_agent_knowledge`: материалы/файлы, версии, enabled, статус извлечения, источник, checksum, фрагменты, привязка агентам.
- `saas_ai_drafts` и `saas_ai_executions`: черновики, подтверждающий сотрудник, итог, история tool calls, использованные источники и версии, ошибки, latency.
- `saas_ai_rules` и `saas_ai_rule_runs`: условия, действия из allowlist, статус, лимиты запусков и ключ выполнения.
- `saas_ai_usage_ledger` и `saas_ai_budgets`: резерв и факт токенов/расходов, agent/model/provider, версия тарифов, timezone периода, дневной/месячный предел. Неизвестные списания не считать нулём.

Инструкции этапов хранить в scope/config агента по фактическим provider + pipeline/stage ID. Лимиты ответов на чат и флаги компании — в config с атомарными счётчиками/резервами в состоянии чата и receipts, если это не требует отдельной таблицы. Длинный перечень таблиц выше — логические сущности, не требование создать каждую физически: при реализации сначала проверить расширение существующих runs/transcripts/commands/outbox. Обязательные индексы: уникальность внешнего события; `(tenant_id, conversation_id, state)`; очередь `(state, available_at)` с выборкой готовых заданий; runs `(tenant_id, agent_id, created_at)`; chunks `(tenant_id, source_id, version)`; уникальность команды триггера по событию/действию.

Сначала проверить возможность расширения `saas_tenant_webhook_events` в inbox и существующих receipts, чтобы не заводить второе хранилище одной операции. Рабочие SaaS сообщения сохранить: добавить internal conversation/provider mapping или связующую таблицу с backfill. Нынешняя уникальность `(tenant_id, external_id)` не описывает независимые провайдеры; изменение делать совместимо, после проверки коллизий, без удаления старого API и истории.

Receipts отправки должны одинаково защищать ручную и автоматическую отправку. Если потребуется новая таблица для агентных операций, обе цепочки используют общий контроль активных отправок. Иначе два разных store обойдут блокировку друг друга.

## 12. Знания, модели, безопасность и расходы

Хранить тексты и фрагменты в PostgreSQL. Для FAQ/коротких материалов начать с структурированного поиска и полнотекстового/лексического ранжирования. На контрольных вопросах AZ/RU/EN измерить полноту поиска: морфология азербайджанского и многоязычный поиск требуют проверки. Если качество недостаточно — embeddings в PostgreSQL с pgvector при доступности расширения. Отдельная векторная БД не нужна.

TXT/PDF/DOCX: лимит размера и извлечённого текста, проверка фактического формата, фоновое извлечение, checksum, источники и версии. Не исполнять содержимое; не переходить по ссылкам документа. Сканы без текста отмечать как требующие OCR; OCR можно отложить. Использовать имеющиеся библиотеки, а новые зависимости обосновать.

Для каждого ответа записывать использованные материалы. Инструкции агента выше клиентских сообщений и документов, но ниже серверных правил доступа. Prompt injection закрывать не только текстовой инструкцией: allowlist tools, проверка схемы и tenant scope, отсутствие прямого SQL/HTTP, ограничение числа шагов и расходов. Недостающие цены/условия — уточнение или handoff.

Контекст формировать последовательно: ограничения приложения → инструкции компании → агент → этап → релевантные знания → разрешённые CRM-поля → история → текущий набор сообщений. Этапную инструкцию применять по текущему ID этапа и её версии. Источники знаний и CRM-факты остаются данными, не привилегированными командами.

Аудио включено в первую версию: переиспользовать транскрипцию и безопасную загрузку, сохранять provenance и cache по ресурсу/версии модели. Изображения также обязательны: загрузка через действующий attachment provider, проверка формата/размера/числа изображений, передача разрешённой vision-модели с контекстом. Учёт стоимости до вызова и fallback при недоступном вложении. Факт успешной загрузки или анализа подписи не считать распознаванием изображения. Для исходящих сообщений не нужна генерация голоса.

Первая модель — через существующую интеграцию OpenAI; конкретную поддерживаемую модель выбрать при реализации по актуальной документации и проверке AZ/RU/EN. Multi-provider API заложить, Gemini/Claude добавить позже. Не закреплять устаревшую модель только потому, что она является текущим значением UI.

Отдельные ключи и budgets по компании, шифрование существующим Fernet; ключи не попадают в prompts, журналы или ответы API. Статистика включает токены входа/выхода, стоимость по версии тарифов, agent/model/tenant, ошибки, ручные подтверждения и handoff. Расходы показывать как расчётную оценку, отдельно от фактического счёта провайдера и Kommo. Резервирование бюджета атомарное, учитывает параллельные задания и другие учитываемые AI-вызовы компании.

Дополнительно лимиты **на чат**: 20 автоответов/час, 60/день, 300/месяц, 500 за всё время. Предлагаемое единое правило: час — скользящие 60 минут; день и месяц — календарные в timezone компании, стартово Asia/Baku; timestamps в БД — UTC. Перед POST резервировать слот атомарно. `accepted`/`sent` учитываются; `unknown` удерживает слот до сверки; доказанный отказ до принятия освобождает резерв. Ручные подтверждения учитываются отдельно от автолимитов, но не обходят денежный бюджет. При пределе поставить причину паузы, показать её сотруднику, не рассылать клиенту повторяющиеся служебные сообщения.

## 13. Небольшие этапы с проверяемым результатом

### Этап A — подтвердить канал до UI

1. Сверить локальный код с выбранной актуальной веткой и production-версией.
2. Проверить тариф/scopes и список ваших каналов, callback и hosting без изменения секретов.
3. Подготовить схему inbox, connection mapping, worker, reconciliation и safety states.
4. После согласования плана реализовать входящие и тесты на fixtures/mock. Обработчик пока только сохраняет события, без ответов клиентам.
5. Отдельно, с разрешением на реальный тест, проверить incoming/outgoing на тестовом аккаунте при закрытом `/app`.

**Выход:** доказан серверный поток событий, новый чат обнаруживается, повтор не удваивает задания, restart не теряет принятые события. Если права/тариф мешают — сначала решить доступность messaging, не объявлять модуль готовым.

### Этап B — агенты и Manual

6. Миграции agents/grants/routes/knowledge/budgets; тест tenant isolation и совместимости.
7. Настройки агента, шифрованные ключи и явные права admin.
8. Текст/FAQ/TXT/PDF/DOCX, назначение материалов и проверка поиска AZ/RU/EN.
9. Context builder с инструкциями компании/агента/этапа, тест инструкции, ручные черновики и вариант автоподготовки по входящему; предпросмотр/редактирование/подтверждение. Подключить транскрипцию аудио и vision для изображений с диагностикой фактически обработанных материалов.

**Выход:** агент с собственной инструкцией и знаниями создаёт проверяемый черновик, источники и стоимость видны. Это промежуточный результат, ещё не полноценная автономная замена.

### Этап C — автоматические ответы

10. Chat queue, batching, leases, revisions и восстановление.
11. Общая цепочка ручной/автоматической отправки в конкретный чат, receipts и unknown reconciliation.
12. Handoff, пауза при ответе менеджера, resume и emergency stop.
13. Лимиты, health, журнал и уведомления о degraded ingress/worker.

**Выход:** Automatic отвечает при закрытом `/app`, выдерживает повторы, рестарт и передачу человеку. Только после этого возможен ограниченный пилот замены KWID.

### Этап D — разрешённые CRM-действия и правила

14. Чтение клиента/сделки, задачи, handoff через безопасные команды; изменение имени/телефона и этапа — через проверенные существующие либо узкие новые команды.
15. Простой конструктор условий на естественном языке и действий из каталога, лимиты триггеров, выполнение once-per-event и аудит. Обязательные сценарии: «Номер получен» и «Новое обращение».
16. Валидировать/нормализовать телефон; неоднозначные данные отправлять на ручное подтверждение. При «Новом обращении» проверять историю и состояние разговора, не создавать автоматически новый лид. Координировать сообщение триггера с обычным ответом, чтобы клиент получил один согласованный ответ.

**Выход:** правила выполняют разрешённые действия, а ошибки/неизвестный результат не превращаются в повторное изменение CRM.

### Этап E — пилот и эксплуатация

17. Полные критические тесты, regression `/app`/`/webapp`, мобильный UI.
18. Документация таблиц/API, переменных, webhook setup, budgets, recovery и rollback.
19. Перенос ваших инструкций, знаний и действующих сценариев KWID; сравнение ответов на одинаковых примерах.
20. Shadow mode: наш AI только готовит результаты, KWID продолжает отвечать. При переходе выбрать одну тестовую воронку и отключить там KWID/Salesbot старой цепочки, чтобы два бота не ответили одновременно.
21. Разрешённый пилот с наблюдением задержки, ошибок, дублей, стоимости и handoff. При откате сначала выключить наш Automatic и проверить незавершённые отправки, затем вернуть KWID.

Сроки оценивать после этапа A: доступ API, история и альтернативная Salesbot-отправка могут изменить объём. Каждый этап завершается отчётом о файлах, тестах и оставшихся ограничениях; автоматическое развёртывание не входит в текущую задачу.

## 14. Приёмка: обязательные сценарии

1. Все сотрудники закрыли `/app`; новый клиент пишет в новый чат → событие и задание появляются без посещения UI, Automatic отвечает в исходный канал.
2. Тот же webhook приходит несколько раз и то же сообщение найдено poll → один ответ.
3. Три сообщения подряд → учитывается полный набор, не запускаются три параллельных ответа.
4. Два workers берут один чат, один теряет lease → старый исполнитель не отправляет ответ.
5. Новое входящее/смена этапа/выключение агента во время генерации → устаревшая отправка отменяется.
6. Менеджер отвечает из `/app` и отдельно из Kommo → AI ставится на паузу; собственный outgoing не вызывает новый ответ.
7. Restart после commit inbox, во время генерации, перед POST и после POST → задания восстановлены, неизвестная отправка не повторена.
8. Коммо принимает POST, но соединение обрывается → `unknown`, сверка/ручное решение; не второй POST.
9. Webhook потерян/отключён → резервное чтение обнаруживает пропуск, health показывает проблему.
10. Новое подключение, новая беседа и одинаковые внешние ID разных tenant/providers → нет пересечения данных или неправильного канала.
11. Исторический импорт и включение агента → старым сообщениям массовые ответы не уходят.
12. Лимит денег исчерпан параллельными заданиями → новые платные вызовы останавливаются; понятное уведомление владельцу.
13. Prompt injection в клиентском тексте/документе → не меняет права и не открывает чужие данные/произвольные tools.
14. Удалённые/отключённые знания и неизвестные цены → данные не выдумываются; handoff/уточнение.
15. Закрытый talk, API 401/402/403/429/5xx, неполная история, файл/голос без текста → безопасный статус и диагностика.
16. Миграции, старый Chat AI, история и ручные отправки, `/webapp`, согласования задач продолжают проходить regression.
17. Клиент пишет на 0-й и 30-й секунде → ответ не раньше 70-й секунды; повтор webhook не переносит debounce. Рестарт сохраняет due time.
18. Аудио и фото → учтено фактическое содержимое; недоступный/неподдерживаемый файл отмечен явно, а не признан обработанным.
19. «Номер получен» → корректный номер/контакт, разрешённое обновление и этап, одна команда на событие и один согласованный ответ. Невалидный/неоднозначный номер не перезаписывает CRM автоматически.
20. 21-й/61-й/301-й/501-й автоответ в соответствующем периоде блокируется, включая конкурентные задания и границы timezone; отключённые flags блокируют POST и CRM-записи.

Mock/stub покрывают всё без внешних сообщений. Реальный аккаунт нужен отдельно для тарифа/scopes, payload, привязки чата, доставки, событий ответов сотрудников и резервного обнаружения новых бесед. Эти проверки и сообщения клиентам выполняются только после явного разрешения.

## 15. Первая рабочая версия и отложенное

**Первая пригодная для пилота версия:** данные поддерживают несколько агентов, но достаточно одного активного агента на непересекающуюся область; инструкции компании/агента/этапа; азербайджанский стартовый язык и сбалансированный стиль; знания и файлы; аудио и изображения; Manual и Automatic; серверный ingress и reconciliation; debounce 40 секунд; защищённая отправка; handoff; журнал; лимиты на чат и компанию; безопасные CRM tools и два обязательных триггера; `/app` desktop/mobile. Автоответы выключены по умолчанию.

**За пределами первой версии:** Gemini/Claude без необходимости для качества, Google Calendar, Make/Zapier, произвольные внешние интеграции, отправка файлов по триггеру, OCR сканов, голосовая генерация/звонки, исходящие кампании/follow-up, полный BeinSystems messaging и прямые Meta/Evolution-интеграции. Также исключены marketplace, сложный workflow builder, новая CRM, обучение модели на переписках и коммерческий SaaS-биллинг. Анализ изображений и входящего аудио не входит в этот список: он обязателен по новому ТЗ.

**Рекомендация к согласованию:** сначала доказать автономный серверный канал, затем агенты/знания, затем безопасная автоматическая отправка. KWID отключать только после прохождения приёмки и переноса тех сценариев, которыми вы пользуетесь.

## 16. Триггеры и CRM: точные границы исполнения

Условие на естественном языке проверяется AI по ограниченному контексту; результат — структурированный кандидат с evidence message ID, параметрами и признаком неоднозначности. Модель не выдаёт сама себе разрешение выполнить действие. Backend проверяет каталог, grant, состояние и идемпотентность команды. Оценка уверенности модели не заменяет валидацию фактов.

«Номер получен»: извлечь кандидат из конкретного сообщения/транскрипции → нормализовать с учётом страны, не приписывать код страны неоднозначному номеру → проверить → сверить правильный контакт сделки и текущий телефон → обновить только разрешённое поле → выполнить разрешённый переход этапа → сформировать один итоговый ответ. При конфликте существующего телефона предложить подтверждение. Подходящий пример после подтверждённого результата: «Təşəkkür edirəm, nömrənizi qeyd etdik, tezliklə mütəxəssisimiz sizinlə əlaqə saxlayacaq.» Текст и обещание связи должны соответствовать правилам компании.

«Новое обращение»: первый подтверждённый входящий в текущем разговоре определяется по provider/conversation mapping, истории и сохранённому состоянию; старый импорт и повтор доставки не запускают его снова. Первый ответ клиента не равен созданию нового контакта/лида.

Каждое действие имеет собственный command ID и outcome; несколько CRM-вызовов не образуют атомарную транзакцию внешнего провайдера. Если телефон обновлён, а этап не изменён, сохранить частичный результат, не повторять обновление и не утверждать клиенту, что всё выполнено. `unknown` блокирует повтор неопределённого действия до сверки. После изменения этапа снова проверить scope перед дальнейшей отправкой.

Команда отправки согласуется с обычным AI-ответом: шаблон может заменить ответ либо стать его частью, но не создаёт независимый второй POST. Для Manual/test внешние действия по умолчанию только предлагаются. Ручное подтверждение действия сохраняется отдельно и повторно проверяет актуальные права, ресурс и значение поля.

## 17. Включение без простоя и состав каждого этапа

### Feature flags

Три независимых переключателя: `ai_agents_enabled` — доступность нового модуля для компании; `ai_agents_auto_send_enabled` — разрешение автоотправки; `ai_agents_crm_actions_enabled` — разрешение CRM-записей. Все первоначально false. Дополнительно общий серверный kill switch может запретить автоматические внешние действия всех компаний. Эффективное разрешение требует всех соответствующих flags, активного агента, Automatic, действующего grant, подходящего scope, бюджета и состояния чата.

Выключенная компания продолжает пользоваться прежним Chat AI и ручной отправкой. Новый worker не должен вызывать её AI или изменять CRM; не регистрировать её новую webhook-подписку автоматически при запуске. Общие миграции должны быть короткими/аддитивными и безопасными при повторе; тяжёлый backfill разбить на небольшие порции. Возможное блокирование DDL проверить на копии существующей БД. Развёртывание без простоя — критерий проверки, не заранее гарантированное свойство любой миграции.

### A. Серверный канал и очередь

- **Файлы:** узкая композиция `bot.py`/`tenant_web_routes.py`; ingress/store/worker/reconcile; расширение `tenant_integration_store.py` и Kommo adapter только для connection identity и capability checks; tests соответствующих модулей.
- **БД:** reuse/расширение webhook events, connection mapping, очередь и индексы ready/unique; tenant context и reconnect generation.
- **API:** отдельный ingress и owner-only diagnostics; без внешней отправки.
- **UI:** максимум диагностика подключения, без создания полного редактора агента.
- **Проверки и завершение:** mock payload, commit-before-ack, новый чат без `/app`, повтор, restart, два workers, replay через poll; реальный канал — отдельный разрешённый тест.
- **Риски:** тариф/scopes, форма payload, неполное discovery, спящий hosting. Не переходить к заявлению об автономной замене, пока путь не подтверждён.

### B. Настройки, знания, медиа и Manual

- **Файлы:** `tenant_ai_agents_api/store/policy/service/knowledge/provider.py` либо компактные эквиваленты; расширение существующего AI transport, attachment/transcription; `docs/tenant-app.html`, новые точечные JS-модули и `ui/src/main.jsx`; tests.
- **БД:** agent config/scopes, этапные инструкции, источники/chunks/назначения, версии draft/run и usage. Существующие `saas_chat_ai_runs`/transcripts расширить только без нарушения старого контракта; иначе новая запись содержит только специфичные агенту данные.
- **API:** CRUD агента, test, знания/upload, draft/review, модельные capabilities; текущие Chat AI endpoints совместимы.
- **UI:** список агентов; вкладки «Основные», «Источники», «Сделки и контакты», «Триггеры», «Каналы и воронки», «Дополнительно». Возможности действий/триггеров включаются по готовности; неподдерживаемые не выглядят работающими. Большой prompt editor и тест, инструкции этапов, реальные модели/каналы; азербайджанские строки, mobile.
- **Проверки и завершение:** tenant isolation, admin capability, AZ/RU/EN поиск и ответы, PDF/DOCX/TXT, аудио/vision, скрытые ключи, Manual не отправляет автоматически и не пишет CRM.
- **Риски:** качество извлечения/поиска, недоступные медиа, стоимость мультимодальности и длинного контекста. Не подключать другого платного провайдера без необходимости.

### C. Автоответы, handoff и лимиты

- **Файлы:** agent worker/state/service; существующие `tenant_chat_send_policy/store/service/provider.py`, notice outbox/policy; компактный чатовый UI-блок; tests конкурентности.
- **БД:** due time/revision/lease, handoff state, общий receipt для send, счётчики/резервы квот и бюджета.
- **API:** enable/disable, emergency stop, chat state/handoff/resume, runs/usage/diagnostics.
- **UI:** агент и состояние в чате, остановка/возобновление/передача, последний результат и ошибка; задержка 40 секунд и лимиты 20/60/300/500 в настройках.
- **Проверки и завершение:** закрытый `/app`, точный канал, debounce, own outgoing, ответ человека из Kommo, перезапуск/unknown, пределы периодов и всех kill switches. Auto flag включается только для разрешённого тестового чата после Manual.
- **Риски:** гонки с внешним менеджером, неопределённая доставка, лимиты Kommo; фиксировать практические ограничения и не обещать exactly-once.

### D. CRM-команды и два обязательных триггера

- **Файлы:** agent triggers/actions; существующие CRM/task/approval commands; узкая contact-update command только при отсутствии готового сервиса; tests; соответствующие вкладки карточки агента.
- **БД:** rule config и action command/outcomes, reuse существующих команд/аудита; unique event/action и ограничение запусков.
- **API:** CRUD triggers, разрешения действий, preview/approve при неоднозначности, история команд.
- **UI:** простой редактор естественного условия и каталога действий; «Номер получен», «Новое обращение», подтверждение конфликтного телефона; без визуального workflow builder.
- **Проверки и завершение:** корректный контакт/телефон/этап, сохранение согласований, два повтора, partial failure, unknown, один итоговый ответ, flags и actor grant.
- **Риски:** неоднозначный номер, устаревшая карточка, частичная CRM-запись. Создание контакта/сделки не включать без отдельной корректной реализации и поиска дублей.

### E. Регрессия, документирование и пилот

- **Файлы:** tests существующих SaaS/legacy функций и новых модулей, документация, только необходимые исправления по результатам; production-конфигурацию текущей задачей не менять.
- **БД:** проверить чистую установку, повтор DDL, обновление копии действующей схемы и сохранность истории; никаких миграций рабочей БД без согласования.
- **API/UI:** совместимость старого Chat AI/отправки и авторизации, понятные журналы и стоимость, mobile; никаких отдельных приложений.
- **Проверки и завершение:** все критические сценарии, тестовая компания → Manual → отдельный тестовый Automatic → разрешённые CRM-действия → ограниченный реальный пилот. Реальная отправка, commit и deployment требуют отдельного согласования.
- **Риски и откат:** два бота в одном чате, необработанные sending/unknown, неверная конфигурация. Выключить новый Automatic и CRM writes, отменить pending, сверить внешние операции; сохранять данные и работу остального приложения. Возвращать KWID на ту же область только после этой сверки.

**Условие отказа от подписки:** на ваших контрольных диалогах проходят все критерии нового ТЗ, включая изображения, аудио, инструкции этапов, телефон, триггеры, 40 секунд и работу без браузера. До этого ручную или только текстовую версию считать промежуточным результатом, а не полной заменой.
