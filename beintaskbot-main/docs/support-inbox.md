# Внутренняя очередь обращений Connect

Реализация для ночной техподдержки Beintaskbot, ветка `feature/support-inbox`, база `0cf99046`.

## Как пользоваться

1. Открыть **AI Agents → Обращения**. По умолчанию показаны все нерешённые обращения; сначала переданные AI человеку, затем ожидающие сотрудника. Очередь обновляется кнопкой «Обновить».
2. Отфильтровать очередь по статусу или ответственному, при необходимости выбрать «Без ответственного».
3. Нажать «Открыть обращение»: видны причина передачи, краткое описание, AI-сводка, предложения агента, следующие действия и локальная история переписки с постраничной загрузкой.
4. Нажать «Взять в работу», чтобы назначить обращение себе и установить «В работе». Можно назначить другого допущенного сотрудника, исправить описание и план действий, сохранить изменения.
5. «Открыть исходный диалог» открывает существующее окно Beintaskbot с обычными средствами ответа через Connect. После завершения нажать «Отметить решённым».
6. Для ручного обращения открыть существующий Connect-диалог и нажать «Создать обращение». Повторное нажатие возвращает то же обращение.

Доступ наследует действующую политику AI Agents: владелец и активный admin с `members[telegram_id].ai_agents_manage=true`. Назначение возможно только такому сотруднику той же компании. Отдельные роли/права CRM не создаются. Для исходного окна диалога действуют его существующие права чтения/отправки; история непосредственно в обращении доступна по правам очереди.

Просмотр, назначение, смена статуса и решение обращения не изменяют Human Mode/Pause/Resume. Ручное создание обращения также не останавливает AI: для передачи диалога используется существующее действие «Передать человеку». Решение обращения не возобновляет AI; это отдельное явное действие сотрудника в текущем интерфейсе.

## Создание и идемпотентность

Первая версия поддерживает локальные WhatsApp-диалоги Connect. Kommo, его ключи, сделки, API и состояние подключения для очереди не нужны. Поле `lead_id` — уже существующий локальный идентификатор Connect-диалога; историческое имя колонки `kommo_lead_id` в общей истории не означает обращение к Kommo.

- `saas_support_tickets`: tenant/channel/conversation, причина, описание, сводка, предложения, следующие действия, ответственный, статус, timestamps.
- `saas_support_events`: постоянная tenant-scoped квитанция события → обращение.
- Частичный уникальный индекс допускает только одно нерешённое обращение для `(tenant_id,channel_id,conversation_id)`.
- После решения допускается новое обращение по новому событию/ручному request_id. Повтор старого события возвращает прежнее решённое обращение.
- Создание и переход в Human Mode выполняются в одной транзакции. Проверяются tenant, активность канала и точная принадлежность диалога; составные внешние ключи дополнительно запрещают чужой канал и чужого ответственного.
- Advisory locks сериализуют создание по маршруту и ключу события. Повторное открытие старого обращения при наличии нового открытого возвращает HTTP 409.
- Обычные сообщения/обычный enqueue не создают обращений. Используются только существующие разрешённые handoff-триггеры и явное действие сотрудника.

Схема устанавливается аддитивно из `tenant_ai_agents_schema.ensure_schema()` до рабочих транзакций; на первом запуске создаются существующие Connect-таблицы при их отсутствии. Миграции не выполнялись на production. Импорт старых Human Mode диалогов до установки этой версии автоматически не производится.

## Точки интеграции при объединении

1. `tenant_ai_agent_actions.handoff`: `handoff_ticket(cur, job, reason)` в текущей транзакции, затем `summarize_created()` после commit. Контракт job: tenant_id, provider, channel_id, conversation_id/chat_id, event_fingerprint. Возвращает прежний bool изменения состояния. Повтор события не создаёт второй ticket.
2. `tenant_ai_agent_connect.finish_sent_after_reply_handoff`: такой же hook после принятого ответа по `handoff_after_reply`. Обращение фиксируется и если оператор уже выиграл гонку перехода в Human Mode; его reason/state не перезаписываются.
3. `tenant_ai_agents_store.set_conversation_state`: ticket создаётся только при Connect `state='human'`. **Terra:** сохранить этот hook и post-commit сводку при объединении Pause/Resume. Для pause/resume ticket не создаётся. Заодно уточнено `c.connect_channel_id` в существующем JOIN, иначе PostgreSQL возвращает ambiguous-column при ручном handoff.
4. `tenant_ai_agents_store.finish_draft_send`: после accepted draft с `handoff_after_send`; канал берётся из сохранённого webhook payload, event key — из source_fingerprint. Не менять эти поля при объединении.
5. **Astra:** в `tenant_ai_agent_connect.py` изменена только функция `finish_sent_after_reply_handoff`. Код распознавания/доставки голосовых, enqueue, history, worker, Connect transport и настройки Nizam Ai не менялись. Сводка использует уже сохранённые body; недоступные аудио и вложения явно отмечаются через существующий history formatter и не додумываются.
6. `tenant_web_routes.ai_agent_routes`: новые маршруты сохраняют существующий prefix; `tenant_web_assets` и `docs/tenant-app.html` подключают отдельный JS очереди. Существующий JS Pause/Resume не редактировался.
7. При объединении проверить staging: повторную доставку одного webhook нескольким процессам, реальный handoff и handoff_after_reply, чтение/отправку в исходном Connect-диалоге под выданными правами, новый deployment с аддитивной схемой и общий учёт лимитов AI. SQL-тесты используют изолированный PostgreSQL/WASM с одной сессией; межпроцессные гонки production PostgreSQL этим запуском не моделируются.

## AI-сводка

Обращение коммитится до AI-вызова. Даже при отсутствии ключа, исчерпанном лимите, недоступном провайдере или некорректном ответе оно остаётся в очереди. Без AI описание берётся из последнего текстового входящего сообщения, либо из причины передачи. Сотрудник может заполнить поля вручную и явно повторить недоступную сводку.

Используется существующий `tenant_chat_ai_provider.generate`, включая выбор company/platform credential через текущую key policy. Для platform соблюдаются доступность агента, enabled/emergency stop, разрешённая модель и tenant token cap; для company — действующие enabled/consent/model настройки. Перед вызовом под общим `tenant-chat-ai:<tenant>` lock резервируется один вызов с учётом **обоих** журналов Chat AI и AI Agents.

Если есть связанный AI Agent, создаётся обычный `saas_ai_agent_runs` и изолированная квитанция `event_type='support_summary',state='completed'`; она не попадает в очередь входящих сообщений. Токены записываются в существующую `saas_ai_agent_token_usage`. Без связанного агента company-вызов резервируется в `saas_chat_ai_runs`. Неизвестный/ошибочный результат остаётся учтённым как потраченная попытка. Никаких новых API-ключей или тарифных настроек не введено.

Контекст ограничен последними 30 сообщениями **точного** tenant/lead/channel; более ранняя переписка и непрочитанные медиа явно помечены как недоступные. Полная локальная история доступна сотруднику постранично. JSON-ответ содержит description/summary/suggestions/next_steps; все поля ограничены по длине и экранируются в UI. Изменения описания, предложений и следующих действий, внесённые сотрудником во время генерации, сохраняются.

Генерация выполняется после commit в текущем вызове (таймаут существующего провайдера до 60 секунд). Отдельный worker, cron или система уведомлений не добавлены. При прерывании процесса после резервирования сводка может остаться в `generating`: автоматического повторного платного вызова нет; само обращение и история доступны. Очередь не требует успешной сводки для работы.

## API

Все маршруты находятся под существующим AI prefix `/api/platform/ai/`:

- `GET support-tickets?status=unresolved|all|new|waiting|in_progress|resolved&assignee=<id>|unassigned&offset=0`: 50 обращений и список допустимых ответственных.
- `POST support-tickets`: `request_id` UUID и `lead_id` либо точные channel_id/conversation_id; необязательные reason/description.
- `GET support-tickets/{id}?before=<message_uuid>`: обращение и 50 сообщений, cursor для более ранних сообщений. Чтение не меняет состояния диалога.
- `PATCH support-tickets/{id}`: status, assigned_to (null снимает назначение), description, suggestions, next_steps.
- `POST support-tickets/{id}/summary`: явная попытка подготовить pending/unavailable сводку.

Каждая мутация требует JSON, правильный Origin и expected_tenant_id/expected_user_id. Права и lifecycle проверяются по актуальным строкам БД при каждом запросе; архивированные/приостановленные компании и неактивные участники закрыты. Ответы no-store; UI отбрасывает устаревшие ответы при смене компании.

## Проверки

Локальные зависимости установлены только в игнорируемые `.venv-support/` и `.support-test-deps/`. Runtime-зависимости приложения не изменены. SQL-тесты используют PGlite 0.5.10, DOM — jsdom 29.1.1, AI-вызовы замоканы; production БД и WhatsApp не используются.

```powershell
python -m pip install -r requirements.txt pytest
npm install --prefix .support-test-deps @electric-sql/pglite@0.5.10 jsdom@29.1.1
python -m pytest tests/test_tenant_support_inbox.py -q
node tests/test_tenant_support_inbox_ui.cjs
# Предзагрузка реального драйвера предотвращает раннюю подмену psycopg старым test stub:
python -c "import psycopg, pytest; raise SystemExit(pytest.main(['tests','-q']))"
```

Проверяются создание при handoff/accepted reply/accepted draft/ручном действии, отсутствие ticket при обычном сообщении и pause, дубли включая уже решённое обращение, составные FK, tenant isolation, архив/неактивный пользователь/запрет роли, назначение и фильтры, статусы/409 при конфликте, неизменность состояния AI при чтении и решении, пагинация истории, AI-сводка и её отказ, общая квота и platform token cap, сохранность правок сотрудника, HTTP Origin/identity, DOM XSS-экранирование и смена компании. Реальный внешний AI-вызов и тестовый WhatsApp-сеанс должны быть проверены на staging при объединении.

- Финальный целевой набор: **48 passed** (28 новых SQL/HTTP-интеграционных проверок и 20 связанных существующих тестов).
- Три JS-проверки: очередь (DOM), сохранение Connect scope, диагностика — **PASS**.
- Python compileall, `node --check`, `git diff --check` — без ошибок.
- Полный regression-прогон: **1223 passed, 12 failed, 4 skipped, 223 subtests passed**. Он выполнен до добавления двух последних дополнительных сценариев очереди; они затем прошли в финальном целевом наборе.
- Все 12 падений воспроизведены на **неизменённом `0cf99046`**, извлечённом в игнорируемую `.support-test-deps/baseline` внутри этого же worktree (проверены те же пять тестовых модулей, 37 passed / 12 failed). Другие worktree не использовались и не менялись.
- Падения базы: ограничение размера startup (1), извлечённые auth/connector routes и SSO (2), существующая проверка Chat AI key binding (1), устаревшие fixtures отправки после Connect routing (7), прежнее ожидание Kommo-only onboarding activation (1). Эти несвязанные участки не исправлялись в ветке очереди.
- Production-деплой, merge, реальные AI-запросы и WhatsApp-отправки не выполнялись.

## Консультация в группе разработчиков

Владелец может подготовить сводку и выбрать группу и конкретные вложения текущего обращения; перед отправкой видны группа и текст. Отправка выполняется отдельным действием. Состояние «отправлено» появляется только после подтверждённого Connect receipt; неопределённая отправка не повторяется автоматически.

В группе ответ связывается с консультацией, если содержит указанный в сообщении `CASE:` идентификатор. Backend также понимает подтверждённый provider message ID, но текущий Connect не передаёт его для цитат, поэтому одно цитирование пока недостаточно. Текст ответа считается непроверенным материалом и не меняет настройки, исход или статус обращения. Владелец может сохранить черновик клиенту; этот путь не отправляет его. После уточнения допускается отдельное подтверждённое сообщение в ту же группу с новыми выбранными источниками; старый код удалённого доступа не подставляется.

Ссылки на вложения открываются через CRM и не передают файлы в WhatsApp: получатель должен уже иметь доступ к обращению и диалогам. При открытии файла права и принадлежность исходному диалогу проверяются заново. Совпадающие по версии сообщения сохранённые media receipts показываются как справочные данные без повторного AI-вызова; текущие байты при этом не проверяются. Отсутствующий или неполный результат не выдаётся за успешный анализ. Этот workflow не назначает агента и не включает автоматические ответы.
