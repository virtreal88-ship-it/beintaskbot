# Customer Memory: physical erasure and concurrency investigation

Scope: read-only code audit of Beintaskbot main `fc75c2899b7b86de42bf2cafdbdd116e9717d821`, draft memory branch, and Connect master `bd0828eb7fa203c4f5bfa3a68e5a71e7a16d585f`; PostgreSQL experiments use a disposable loopback database and synthetic data. This is not an audit of live infrastructure, its schema, database clients, or production data.

## Known contact removal paths

* The native contact API maps the UI delete/archive action to `archive_contact`; `tenant_crm_native_contacts.py` updates `archived_at` and commits its own transaction. It does not physically delete the CRM contact. Existing code and tests do not establish that the physical-delete bug affects this archive action.
* `saas_crm_native_contacts.tenant_id` references `saas_tenants` with `ON DELETE CASCADE`. A physical tenant DELETE can therefore cascade to contacts. A synthetic one-tenant test with no blocking dependencies completed while a channel gate was held: the draft contact trigger found the tenant absent and returned before taking that gate. This does not establish tenant-erasure safety for other dependency graphs or in-flight AI/HTTP contexts.
* Native contact identity and conversation links and Customer Memory child rows have `ON DELETE CASCADE`; deals and tasks can have `NO ACTION` contact foreign keys, so a direct physical contact DELETE may fail for reasons that predate Customer Memory. Deleting a CRM company is not itself a cascade to its contacts. See `tenant_crm_native_schema.py` and the actual deployed schema before relying on these claims.
* Search of the main checkout found direct physical DELETE of native contacts and tenants in synthetic tests, not an application deletion handler. The dynamic table DELETE in `tenant_connect_reconcile_dependencies.py` is constrained to its listed dialog dependency tables, which do not include native contacts or tenants. Some test fixtures use `TRUNCATE saas_tenants CASCADE`; PostgreSQL TRUNCATE does not fire row DELETE triggers and is not an erasure-fence test.
* Connect's own checkout uses its Prisma models and webhook/SSO APIs. No reference to the Beintaskbot `saas_crm_native_contacts` or `saas_tenants` tables was found in its source/schema at the revision above. This is not evidence about all deployed integrations, direct SQL clients, administrative scripts, database roles, backup restoration or Railway operational procedures.

## Observed concurrency and candidate experiment

The checked-in trigger takes a nonblocking exclusive channel transaction lock after PostgreSQL locks the contact row. An in-flight read of another contact can therefore make direct physical DELETE fail with `55P03`, including when the memory flag is off. A prior blocking lock variant allowed two multi-statement deletions to lock channels in opposite order and deadlock with `40P01`. Three explicit release tests are intentionally red; the draft cannot be merged or deployed until the actual CRM operations satisfy them.

An isolated *experiment* registers each active reader using a unique session lock and a short committed registration under an exclusive channel registration gate. Deletions take shared channel and per-reader locks, which are mutually compatible across deletions but wait for a registered reader. Synthetic tests show that this arrangement can order a read against deletion and let two independent channel guards be obtained in opposite orders. It is **not an implementation or approved fix**:

* A REPEATABLE READ transaction whose snapshot precedes registration cannot see the later reader row. A marker `FOR KEY SHARE` did not detect a non-key marker update; `FOR SHARE` produced `40001` in a synthetic test. That fails closed but still aborts a caller's physical DELETE and requires transaction retry by every affected client. There is no evidence that external clients provide it.
* In the actual schema, unique channel, route and source tombstones are another source of cycles: crossed `INSERT ... ON CONFLICT DO NOTHING` operations in two transactions reproducibly produce `40P01`. Independent synthetic PostgreSQL tests reproduced the unique-index cycle for channel, route and source fence tables. Existing memory APIs also produced two route tokens shared by the history of two contacts via confirm, revoke and reassignment; a full trigger-level deadlock for every overlapping source/route scenario has not been demonstrated. An append-only per-erasure event can avoid this *particular* key collision, but needs bounded retention, provenance, tenant isolation, migration and complete read/cleanup design.
* Readers must never wait on a contact or another lock held by a deleter that waits for the reader. All post-registration lock paths need a proven NOWAIT/cleanup order, including multi-channel operations, failures, process crashes, session loss, and source/identity changes. A session lock on one connection does not protect context that continues on another connection after the locking backend dies.
* Session/advisory locks ending with the read transaction do not protect a Python object, an HTTP response, an AI request, or a generated draft after that transaction. Erasure, source ACL, assignment and identity revocation need a common, bounded, independently reviewed invalidation protocol through actual dispatch and final delivery. A plain version SELECT immediately before dispatch has a TOCTOU race. See `customer-memory-dispatch-boundary.md`.
* Registration cleanup cannot use age alone to infer that a reader is dead. It must prove lock ownership is gone and preserve fail-closed behavior if the cleanup or registry is unavailable. Pooling, backend loss, registration failures, token collision, tenant cascade and monitoring/performance remain unverified.

Do not use the experiments to enable the feature, modify production, infer permission to process real historical data, or claim fact-extraction quality. The source of physical deletes and transaction isolation for all real consumers remains unverified. CI must keep the three physical-erasure tests as a release gate; successful synthetic lock experiments do not replace them.
