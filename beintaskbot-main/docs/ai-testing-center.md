# Центр тестирования AI Agents (/app)

После объединения открыть `/app` → **AI Agents** → **Тестирование**. Главное меню и пилотный `/webapp` не меняются. Нужны действующее членство владельца или admin с `ai_agents_manage`, включённый AI компании, включённый агент и разрешённый сервером AI-провайдер.

## Реальные источники

**Kommo:** выбрать агента, собственную подключённую компанию, сделку из локального каталога, контакт сделки и Talk/чат. Каталог выполняет только GET через существующий tenant-bound адаптер. Поля маршрута доступны только для чтения. Затем сохранить выключенную привязку, подтвердить номер компании, проверить существующим механизмом и включить её. Проверки account/lead/contact/Talk/chat/origin и двух серверных разрешённых номеров сохранены. При отсутствии разрешённых номеров проверка закрыта.

**Connect WhatsApp:** выбрать агента, собственный активный канал и уже полученный подписанным webhook диалог. Существующие webhook/очередь/worker продолжают создавать черновики. Даже Automatic не отправляет ответы Connect Test Mode. Существующий backend запрещает также ручную отправку таких тестовых черновиков; этот запрет сохранён. Для обычных разрешённых черновиков действуют существующие права и отдельное явное подтверждение отправки.

Привязки независимы по источнику. `agent_id` добавлен в существующие таблицы привязок. Новая UI всегда передаёт выбранного агента; старые клиенты без этого поля сохраняют прежнюю привязку. Старые записи с NULL сохраняют прежнее поведение до явного выбора. Очереди фильтруют агента только в Test Mode; claim/load/reserve/complete, финальные CRM-проверки и проверка черновиков повторно проверяют актуальную привязку. Отключение Kommo Test Mode отменяет только выбранные тестовые Kommo jobs. Active Mode, Connect и другие контакты не затрагиваются.

**Важно:** привязка сама по себе не переключает компанию из Active Mode в Test Mode. UI объясняет это и требует отдельного осознанного изменения существующей настройки компании. Открытие центра не меняет режимы, инструкции, Nizam Ai, Human Mode и рабочие диалоги.

## Виртуальный чат

Это собственная текстовая история пользователя, не реальный Connect/Kommo-диалог. Можно выбрать агента без внешнего источника или существующую область его правил. Контекст области берётся с сервера, произвольный channel/contact из браузера не принимается.

Используются существующие `tenant_chat_ai_provider.generate`, выбор credentials/model, инструкции компании/агента/области, серверная политика безопасности и фильтр ответа, поиск активных общих/агентских знаний, `matching_triggers`, `should_handoff`, `phone_candidate`, расписание и лимит ответов. Расписание проверяется по реальному текущему времени, включая его timezone. Задержка агента показывается как симуляция без ожидания.

В trace видны знания, совпавшие триггеры, предполагаемые действия и состояние. Единственное реальное внешнее действие — платный запрос к действующему AI-провайдеру. Генератор не получает инструменты. Ни transport, ни исполнители действий, ни CRM/Linear/webhook API не передаются виртуальным маршрутам. Внешние действия в trace всегда имеют `simulation=true`; `real_actions=[]`.

`saas_ai_test_sessions` и `saas_ai_test_turns` хранят только виртуальные состояния/сообщения. Не создаются рабочие webhook events/jobs/drafts/conversation states/messages/support tickets/notifications. Все чтения и записи ограничены tenant и автором сессии; членство и права проверяются из PostgreSQL при каждом запросе и после генерации. Архивированные/приостановленные компании закрыты. Реальный Human Mode не читается и не изменяется, поскольку виртуальная сессия не связана с production-диалогом.

Pause/Human Mode/Resume управляют только виртуальной сессией. Аварийная остановка компании, серверный выключатель, выключенные компания/агент и закрытое расписание блокируют генерацию. Resume не обходит аварийную остановку и не переигрывает сообщения: история для следующей генерации содержит только завершённые ответы. Изменения настроек/версии/прав, Pause и Human Mode во время запроса отменяют показ позднего ответа, сохраняя его расход.

UUID сообщения — ключ идемпотентности. Повтор возвращает сохранённый результат и не запускает провайдера снова. Ошибка/отмена провайдера оставляет `unknown` с удержанием квоты. Незавершённую попытку старше пяти минут можно оставить unknown и начать новый запрос; старая не воспроизводится и поздний ответ не публикуется. После потери сети UI предлагает проверить результат или повторить тот же UUID. При смене компании/пользователя история и незавершённый ввод очищаются, старые ответы игнорируются.

## Учёт лимитов и схема

Аддитивная схема подключена к существующему `tenant_ai_agents_schema.ensure_schema`. Никаких дополнительных сервисов или конфигурации Railway не требуется.

Виртуальная попытка резервирует один вызов в существующем общем журнале `saas_chat_ai_runs` (`lead_id=0`, `config_version='virtual-test'`, без содержимого диалога). Это исключительно общий учёт квоты: реальные Chat AI и Agent budgets уже читают этот журнал. Используется тот же advisory lock `tenant-chat-ai:<tenant>`. Дневной call limit включает реальные и виртуальные попытки, включая неизвестный результат.

`tenant_ai_testing_budget.TOKEN_USAGE_SQL` добавляет виртуальные фактические токены и незавершённые резервы к существующему platform token budget. Его читают virtual admission, agent reservation, support summary и существующая повторная проверка после voice. Изменения voice ограничены этим чтением бюджета; обработка аудио не меняется. До генерации резерв оценивается консервативно: UTF-8 байты ограниченного prompt/history/context плюс максимальный output существующего провайдера. Известный фактический расход заменяет резерв; отсутствие usage сохраняет его до конца UTC-дня. Данные сессий не удаляются через UI. Удаление агента с тестовой историей закрыто понятным 409: агент можно выключить. Это сохраняет историю и не позволяет обнулить платный расход удалением агента.

Ограничения первой версии: текстовый чат, до 8000 символов сообщения, 100 сообщений на сессию, 100 новых сессий в сутки на пользователя, список последних 20 сессий. Нет проигрывания исторических расписаний, загрузки вложений/голоса, симуляции webhook payload или реальных отправок. Новый текст интерфейса — русский; существующие элементы Test Mode сохраняют имеющуюся локализацию. Неизвестный расход учитывается консервативно.

## Интеграционные проверки

1. Запустить существующую инициализацию AI schema до запуска web/worker. Проверить оба новых agent FK и две private-таблицы на staging PostgreSQL, повторный запуск без потери данных. Старые NULL bindings работают по прежним правилам.
2. При объединении с надёжностью Astra сохранить выбранного агента во всех admission/recheck предикатах и общий token budget, включая повторную проверку после транскрипции. Сам AI worker не переписан.
3. На staging с разрешёнными номерами проверить Kommo GET-каталог, реальную строгую verify-последовательность и смену привязки во время обработки. Для Connect проверить два разных контакта и два агента: черновик создаёт только выбранная пара, отправок нет.
4. Проверить виртуальную генерацию через разрешённую platform/tenant модель, knowledge/triggers, исчерпание общего лимита, Pause/Resume/аварийную остановку во время генерации, отзыв прав и переключение компании.
5. Проверить загрузку новых no-store assets и кнопку в существующем модальном рабочем месте оператора. `/webapp`, production и Railway в этой ветке не изменялись.

Автотесты используют изолированный PGlite и mock AI/Kommo; реальных платных запросов и сообщений тесты не выполняют. UI проверяется на реальной разметке `/app`, включая поздние ответы, повтор UUID, XSS и отсутствие API отправки/изменения общих настроек.

Для повторения тестов локально (Node.js и зависимости Python из requirements плюс pytest):

```powershell
npm install --prefix .support-test-deps @electric-sql/pglite@0.5.10 jsdom@29.1.1
python -c "import psycopg,pytest; raise SystemExit(pytest.main(['tests','-q']))"
node tests/test_tenant_ai_testing_ui.cjs
```
