# Customer Memory events and cost: research only

This is not an event queue or an implementation of automatic memory updates. No memory event hooks, worker, migration, paid call, customer message or feature activation were added. A separate unconnected queue would neither reliably observe source changes nor complete this feature; adding one is premature until the CRM erasure/identity/ACL boundary is independently reviewed. The tests cited below use synthetic data on disposable loopback PostgreSQL.

## Existing code and integration points

* `tenant_connect_transport.py` writes inbound/outbound Connect messages and calls `tenant_knowledge_live_queue.enqueue` inside the message transaction. This shows a possible transactional-outbox hook: an event receipt could commit or roll back with its source. Existing upstream provider receipt deduplication and identity-conflict checks are essential. An optional hook must never roll back ordinary message ingestion; any savepoint/timeout fallback must be reconciled without losing events. Employee/AI/uncertain authorship and unverified groups must remain distinct. Existing support queue events and worker are **not** customer memory and must not publish private facts to shared knowledge.
* `tenant_support_inbox_store.complete` writes a `saas_support_completions` request receipt and updates the ticket in one transaction. The update sets workflow `status='resolved'` even when `completion_outcome` is `recommendations_unknown` or `unresolved`; neither an instruction nor a workflow-closed status proves customer confirmation. `resolved_confirmed` is a staff-selected outcome, so source evidence and provenance still need validation. Ticket status, assignee and next action should be projected from the current case rather than duplicated as authoritative memory. Other support updates and message attachments need equally scoped event coverage.
* Native CRM contact/company mutations update `updated_at` within their own transactions, but the audited paths do not emit a customer-memory change event. A contact's company can change, a number can transfer, and direct-route mappings do not prove stable identity. A deterministic structured CRM projection may be useful without AI, but identity, effective dates, access, manual overrides and revocation must be settled before treating an update as a fact. Group authors and fact subjects cannot be inferred from the group route.
* `tenant_media_evidence.persist` stores existing source-bound receipts and `tenant_support_case_context.fingerprint` incorporates `tenant_media_evidence.publication_fingerprint`. A previously missing transcript can arrive without any new message ID or change to message body. A future adapter needs a receipt-version change signal and must reuse the already saved result; it must not run media analysis. Fingerprints must not become unsalted permanent tombstones for secret content. Existing hash/version behavior needs review for harmless receipt timestamp-only rewrites before expensive processing is admitted.
* `tenant_knowledge_campaigns.claim` uses per-tenant serialization, fragments, explicit approval and call/token reservations; expired/incomplete work is fenced as unknown. These patterns are useful, but the campaign model is linked to knowledge extraction and its grants cannot be repurposed for personal-memory work. Existing media grants or budgets for unrelated work do not authorize a memory pilot.
* `tenant_ai_spend_budget.reserve` is an existing accounting primitive. A missing cap with no campaign and no `track_uncapped` returns no reservation; `track_uncapped` alone does not impose a cap. For a repeated call key, `reserve` can return the prior reservation ID even when its state is `unknown` or `settled`. The future memory worker must require an explicit memory-specific budget/limits, check attempt state and separately prevent another dispatch. A reservation ID by itself is not permission to make another call. Normal response input tokens are part of the existing response usage, without a second charge.

## Findings demonstrated by isolated tests

`tests/test_customer_memory_event_research.py` exercises the actual existing primitives without running `tick()` or calling a provider:

1. With the existing extraction switch off, `enqueue` does nothing; in a transaction, source insertion and queue receipt both roll back together.
2. A new message received while a queue generation is running leaves a new pending generation after the old one finishes.
3. The existing live queue itself remembers only the most recent message ID: adjacent duplicate A/A is ignored, but A/B/A produces generation 3 and moves the last-message pointer back to A. A newly ingested message with an older event time can also move the pointer to an earlier point in the conversation. Its implementation explicitly relies on upstream event deduplication; it is not an independently idempotent Customer Memory event log.
4. A synthetic saved audio receipt changes the media evidence fingerprint. Calling the existing live queue with the same message ID again does not create a new generation, so receipt changes need their own signal or reconciliation.
5. The budget ledger returns the same synthetic reservation after settlement as `unknown`; a future worker must fence another dispatch and retain the reserve. The test deliberately makes no AI request.

These experiments establish behaviors in the existing components, not quality of facts, complete source coverage, permissions, or safety of a new integration.

## Requirements for an implementation

* Separate default-off process/tenant controls from any backfill campaign. No workers, bulk scans, approvals or grants start on deployment. A later enablement must not authorize historical processing; paused/stopped jobs must not launch a new provider call.
* After the identity/erasure design is fixed, write opaque, tenant-scoped, source-versioned event receipts in the same transaction as permitted source mutations where possible. Do not put message text, transcription, secrets or generated summaries in the queue. Define identity-link and ACL invalidation as synchronous security fences, not merely an eventually processed event. Cover case transitions, CRM changes, direct client messages, late/reordered events and media receipt changes; do not observe private employee Copilot sessions.
* Deduplicate by a durable event/source-version key rather than only the last event. A late event must not move the processing checkpoint backwards or be dropped just because its `happened_at` is old. Distinguish event time, ingestion order and source validity. Debounce normal messages into bounded batches with a maximum delay, maximum source/byte count, bounded parallelism per tenant and globally, retry limits, checkpoints and a pause/resume protocol. A changed receipt must enqueue the correct source even when the source message is unchanged.
* Re-read current source, identity, subject, group attribution, access and deletion fences in the worker. Missing/ambiguous identity remains scoped to a case or route and cannot automatically create a person/organization fact. Do not silently bind multiple clients by phone. On write, compare identity, source, fact and memory versions under the reviewed transaction protocol; manual edits and tombstones win. A stale result must not overwrite a newer fact. Reliability and source provenance are separate: automatic extraction begins as requiring review.
* Before **any** eventual paid provider call, require an explicit authorized memory-specific budget, reserve a conservative upper bound using the existing accounting primitive, enforce calls/tokens/currency/concurrency independently, and fence `unknown` or already-dispatched attempts. A zero/missing cap or stopped campaign must not be interpreted as unlimited authorization. Distinguish initial build and update in accounting; provider result unknown cannot be automatically retried. No paid execution is authorized by this research.
* Before connecting any hook, prove source transaction rollback and duplicate/reordered delivery, new media receipt after message, case close versus confirmed outcome, tenant isolation, revoked/split identity, deleted source during processing, manual override versus stale result, pause/restart/unknown, budget exhaustion and ingestion failure isolation in real PostgreSQL. Then independently review and measure the effect on existing CRM/message writers. A disabled local prototype or synthetic tests are not evidence that automatic memory is functioning or that extracted facts are accurate.
