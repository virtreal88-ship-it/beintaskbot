# Customer Memory: erasure and dispatch design choices

Status: **design investigation only**. None of the alternatives below is implemented in the production request path, and none makes the current draft migration safe to deploy. The three physical-deletion release tests stay mandatory. The feature is off by default; the production flag state has not been checked.

## The boundary that must be explicit

A database commit and a third-party HTTP request cannot be made into one local atomic action. If a worker checks permission and then pauses before sending, deletion may commit in the gap. Conversely, if bytes have already left the system, a later deletion cannot recall them from the provider. The current `before_dispatch` callback returns before `requests.post` starts and does not close that gap.

A short transaction can instead establish **admission**: a durable decision that an operation may proceed. Admission is not proof that an HTTP request was sent or received. If admission commits before an erasure request, the operation may physically start the HTTP request afterwards unless it is reliably cancelled by a coordinated transport. Any product contract that treats admission as the beginning of an in-flight operation must say so explicitly. A receipt contains opaque IDs/versions, not facts, credentials or a copy of the prompt. Provider charges and unknown outcomes use the existing reservation ledger; an uncertain call must not be automatically retried.

| **A. Keep memory and its migration unshipped.** | Existing contact/tenant deletion is unaffected by this feature. No memory reaches agents. A runtime flag alone is insufficient if the current trigger has already been installed. | No new retry requirement. This does not determine how external SQL clients behave. | Safest immediate state, but does not deliver Customer Memory. Neither C nor D is safe if the current `ON DELETE CASCADE` physically removes the only lifecycle record while an admitted request exists. Decoupling requires a durable, non-content erasure coordinator record that survives the relevant tenant/contact deletion long enough to gate and reconcile work, while avoiding durable personal values. A database trigger that simply exits when a tenant disappears or an asynchronous CDC consumer that may lag is not that coordinator. The same requirements apply to source, identity and access revocations, not only contact deletion.

## Why changing the lock alone is insufficient

The current trigger's channel try-lock can abort a physical contact DELETE with `55P03`; waiting for exclusive locks can deadlock across multi-channel transactions. Crossed unique inserts into channel/route/source tombstones independently deadlock. Append-only erasure events with unique technical IDs and non-unique lookup indexes can avoid that **particular** collision, but require dual-read/rollback design and do not establish the dispatch boundary.

An experimental reader registry with shared deleter locks worked for selected `READ COMMITTED` synthetic cases. Under a pre-existing `REPEATABLE READ` snapshot, a row marker can cause `40001`, so it does not preserve arbitrary existing DELETE transactions without retry. A non-MVCC lock-manager experiment shows a live advisory-lock marker can be visible even under a pre-existing `REPEATABLE READ` snapshot. It also shows that closing the database session leaves an already materialized Python value untouched. A complete registry still needs proof of atomic publication, tenant/channel scope and collisions, reader crash cancellation, identity/link snapshots, bounded scans and deletion latency. A session lock also cannot protect an object or network operation that continues after its database backend dies. None of those experiments is wired into CRM or an agent.

## Decision required before release

The owner must choose the semantics of **erasure completion and earlier-admitted operations**. Specifically, decide whether an operation admitted before a deletion request may physically start afterwards, and whether local erasure may remain pending while an old sender cannot be proven fenced. Separately choose how a minimal ledger retains an unknown provider/billing outcome after sender fencing and local data removal; that uncertainty alone need not prevent local erasure completion. If neither is acceptable, a coordinated transport and cancellation capability must provide a stronger enforceable boundary; a local database recheck alone cannot meet that requirement.

Independently of that decision, implementation cannot claim compatibility with raw SQL or tenant cascade until all physical-erasure writers, their isolation/retry behavior and enforcement mechanism are established. Unknown external writers are not permission to silently alter their behavior. No mass backfill, production rollout or paid pilot is authorized by this document.

## Executable experiment, not integration

The synthetic `tests/customer_memory_erasure_model.py` and its tests implement a minimal admission/pending/drain state machine on disposable PostgreSQL. They contain no real facts, transport, credentials, CRM trigger or agent integration. They deliberately show that a model or delivery operation admitted before pending may physically begin later. Pending blocks new admissions, and this deliberately conservative model blocks its completion transition on an admitted or unknown operation. It does not separate a provably fenced sender from an unknown provider/billing outcome; the latter can remain unknown without necessarily delaying local erasure after fencing and data removal.

The modeled `completed` state does **not** physically delete customer data. Outcome labels stand in for an operator assertion; the model does not authenticate evidence, prove the provider's outcome or fence a paused worker. A real crash may leave an admission indefinitely unresolved. The experiment does not establish source/agent ACL, arbitrary SQL or tenant-cascade compatibility. These gaps remain mandatory engineering and review work, not authorization to enable the feature.

Fencing must cover more than a Python worker: a proxy, socket buffer or other controlled transport that still holds and can transmit payload also needs to be quiesced or fenced. If this cannot be established, local transfer/erasure completion cannot be asserted. Data already outside the system cannot be recalled or claimed deleted at the provider merely because the local erasure completed.
