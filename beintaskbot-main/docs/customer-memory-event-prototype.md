# Isolated Customer Memory event-receipt experiment

This is a **test-only experiment**, not automatic Customer Memory. It is not registered in application schema or any existing CRM, case, message or media writer; there is no background worker, fact extraction, memory write, AI call, client message, paid budget, rollout or feature activation. `tests/customer_memory_event_receipts_prototype.py` requires an explicitly opted-in loopback database named `customer_memory_test` and schemas named `synthetic_memory_events_<random hex>`. A loopback endpoint could be forwarded elsewhere; the operator must independently verify that the database instance is disposable. It must not be used in production or considered a production-safe authorization boundary.

The synthetic scope/subject IDs, source IDs and source-version UUIDs are opaque inputs. No phone number, body, transcript, fact value, secret or generated summary is stored. These UUIDs are **not** an implementation of source authentication or cryptographic content fingerprinting: real producers would need a reviewed durable source-version/receipt identifier, key rotation and source ACL. Scope identity is supplied by the caller; this prototype neither confirms a CRM identity nor attributes messages/groups. The shared monotonically allocated sequence is internal and must not be exposed across tenants in a real implementation.

The local prototype keeps per-tenant/scope receipts, an idempotency key over source kind/ID/version, a checkpoint and a default-paused state. The same A/B/A versions are deduplicated; a new version of the same media source is distinct. Event time is stored separately from ingestion order so a late historical event can still be processed after an earlier checkpoint. A conflicting timestamp for the same source version is rejected. Batches contain at most ten receipts. A bounded first-event coalescing window cannot be indefinitely postponed by more messages; it is a fixed-window/leading-edge policy, not a claim of production-tuned trailing debounce. A claimed batch records a lease/token and a finish advances only its claimed checkpoint. Pause while idle and resume work; interruption or lease expiry while running quarantines the scope rather than silently replaying an unknown attempt.

A per-scope row is locked before allocating an ingestion sequence, so two concurrent transactions on that scope cannot commit later sequence numbers ahead of an uncommitted earlier event. Rollback may leave sequence gaps; those are harmless. Synthetic tests demonstrate commit/rollback order. This lock has **not** been integrated with real writers: a real writer may hold source rows or multiple scopes first, and arbitrary lock ordering can create the same kind of CRM delete/deadlock regression found elsewhere in this draft. Existing ingestion must not be changed until those lock orders, failure isolation, reconciliation and performance are designed and independently reviewed. Synthetic rollback of a fake source and receipt demonstrates transaction capability, not production atomicity.

The local implementation deliberately lacks source/identity/ACL and tombstone checks, CAS on actual memory changes, organization/group attribution, case status projection, source-event coverage, quota/storage cleanup, a global or tenant scheduler, cross-worker fairness, cost reservations, an unknown-provider outcome ledger and post-crash resolution. It cannot safely apply facts or invoke a provider. An unknown lease is permanently blocked until a future reviewed recovery protocol; there is no silent retry. A genuine source hook, bounded worker and approved budget are prerequisites, not implied by this experiment.

`tests/test_customer_memory_event_receipts_prototype.py` verifies synthetic PostgreSQL behavior for idempotency, late events, changed media receipt versions, bounded batches/coalescing, checkpoints, pause/resume, stale/expired claims, tenant/scope isolation, transactional rollback, and commit-order serialization. It performs no model or media calls and sends no messages. These tests cannot establish factual accuracy, production coverage, performance or compatibility.
