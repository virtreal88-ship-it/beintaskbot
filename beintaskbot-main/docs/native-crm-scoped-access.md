# Native CRM scoped access

Implementation is behind `TENANT_SCOPED_ACCESS_ENABLED`; it is not an approval to enable the rollout. With the gate off, the contact directory uses its original company/deal routes and guards; the new narrow contact and deal-company relation routes reject with `scoped_relation_unavailable` (403). Company-card contact unlink keeps its legacy delete check when off. The server explicitly supplies the UI relation mode and row-specific company relation capabilities; the browser never infers rollout from role or a guessed scope. The native sections are `deals`, `customers` (contacts), and `companies`. An absent cell retains its previous native CRUD permission, without converting a provider permission into an all-record scope.

## Covered boundaries

- Native contact collection, direct contact read, creation, update, and archival.
- Source-qualified contact directory: native authority is applied before search, source totals, pagination, and row action flags. Kommo identities, pipeline restrictions, account provenance, and read-only actions remain separate.
- Native deal collection/detail, creation, update, archival, and form options. Options are usable for a permitted create/update action independently of view. Contact options require the current contact view permission when either contact or deal scopes are active.
- Native company collection/detail, creation, update, archival, and related lists/counts. Activated contact/deal scopes restrict their embedded lists and counts without leaking inaccessible IDs via totals.
- Every HTTP handler forwards the authenticated actor to its store. The store rereads current active tenant/membership, workflow grants and department under database fences. Writes authorize and lock the target inside the same transaction. Department mutations use the common tenant fence; department-scoped writes also lock and recheck the responsible membership.
- New human-created records receive immutable `access_responsible_id=actor_id`. Existing `responsible_id` retains its previous operational assignment meaning. Client payloads never set access ownership. Idempotent creates under the matrix cannot return another creator's document.

A readable deal includes its existing contact and company information even when those directories are closed. That embedded context does not grant independent client updates. Updating an existing deal's contact link (including unlinking) requires only the update scope of that deal. Updating a contact card's deal link uses the contact-specific `link_deal` / `unlink_deal` action and requires only that contact's update scope, not deal update or either delete permission. This narrow route changes no other deal field and returns no deal contents. Unlink checks that the deal currently points to the exact authorized contact. The target always stays inside the same tenant; unrelated deal lists are not expanded by this permission.

The company selector and company tab inside an existing contact card use the contact-specific `link_company` / `unlink_company` actions. Both require only that contact's update scope, even when company view/update/delete and contact delete are denied. The transaction locks the authorized contact and a tenant-bound active company, changes only `contact.company_id` and its modification time, and returns a narrow relation receipt with no company fields. Unlink is conditional on the exact current company. The company row, including its modification time and hidden owner, is never changed. A denied company collection does not expose alternative targets; the UI can still detach the already known company. Creation alone does not grant permission to change a company link: the separate post-create link operation also requires contact update authority.

With the gate on, company-card contact link/unlink similarly requires only U of the source company, never contact R/U/D or company D. Both directions lock the contact before the company, preventing an opposite-direction lock cycle. The target contact stays tenant-bound and active; unlink checks its exact current company. Only its company relation and modification time change. The company card does not expand the contact list or contact fields; a denied target list does not break the readable company card. Company-card deal link/unlink now follows the same source-company U rule. The deal-specific `/deals/{id}/company-link` endpoint instead requires U of that deal. Both directions lock deal before company, change only the deal company FK/revision, require active same-tenant targets, and condition unlink on the exact current company. Neither grants target-directory access or changes responsibility. With the gate off the existing company route retains its original dual-U link and company-D unlink checks; the new deal-specific route is unavailable.

During scoped deal creation, the initial contact is authorized by deal C and the exact contact’s current R, not contact U. The create transaction checks and locks the contact, its tenant/activity and applicable view scope before insert. An inaccessible, archived or foreign contact cannot be selected with a forged ID. C alone does not open a contact directory. Initial company binding remains a separate existing-card U action after creation.

## Explicit rollout blockers

1. Company↔deal source-card U and initial-contact C+R semantics are implemented locally. Changing deal channel/conversation links remains an explicit unresolved relation contract. Existing relation changes still require the provider safeguards below.
2. Trusted integration/AI/background stores do not have an authenticated human actor. They retain their separate existing integration authority and create NULL access owners, visible only to an all scope. Deciding how future automatically created documents acquire a human responsible person remains necessary before a complete rollout. Historical-owner backfill is owned by the shared schema migration, not by this code.
3. The legacy provider queue still exports full configured records. New scoped scalar changes use a separate immutable actor/revision/field-mask journal and account/generation-bound identity checks, with current authorization revalidation. A persistent per-record provenance barrier prevents actorless full-record exports after scoped entry, including flag rollback. Per-card legacy admission fencing and durable possible-send evidence protect the first scoped mutation from tracked in-flight legacy requests; unresolved legacy outcomes block scoped delivery. This does not establish a production-ready external relation adapter. New narrow relation routes never enqueue a full-record sync. If the modified entity type currently has outbound or bidirectional synchronization with nonempty allowed fields, these operations return `scoped_relation_sync_not_configured` (409) before any mutation; the UI explicitly says the link was not changed. This is a temporary safe blocker, not a release-ready synchronization design. Provider-specific relation-only API semantics remain under independent investigation; no real provider calls were made.
   Confirmed provider boundaries from read-only documentation research:
   - Kommo has relation-only [link](https://developers.kommo.com/reference/linking-entities), [unlink](https://developers.kommo.com/reference/unlinking-entities) and [filtered relation read-back](https://developers.kommo.com/reference/linked-entities) endpoints. A contact-card deal change must operate through the lead endpoint, not an unsupported contact→lead endpoint. [Cardinality](https://developers.kommo.com/docs/subject-area) differs from the local single contact FK: a lead can have multiple contacts. The approved local interpretation is the main contact: narrow planning replaces/unlinks only the old main while preserving secondary contacts. It does not authorize rewriting the complete contact list. Documents do not promise idempotent repeated POST, atomic company replacement or conflict-free retries after a timeout.
   - Legacy external mappings remain unverified and cannot be reused as account-bound identities. A separate relation identity schema supports account/generation binding; that infrastructure does not verify existing IDs or prove company/provider mappings. Reconnect invalidates prior bindings. Company relations cannot be sent by guessing an external ID.
   - BEIN ERP's current implementation PATCHes `crm/leads/{id}` with `partner_id`; a confirmed relation-only clear/unlink payload and provider idempotency guarantee have not been established from [its documentation](https://docs.beinsystems.az/docs/api/). Existing client headers alone are not proof of server behavior.
   - Durable relation identity/outbox/head schemas, immutable source-card actor/action events, transaction-bound local mutation, authorization fences, and a one-step conditional-delivery driver are implemented. They are dormant: normal relation routes do not call the driver and no production provider adapter is registered. The driver requires atomic compare/apply semantics; a GET followed by POST is not remote CAS. Unknown timeout/crash outcomes are not replayed or treated as completed.
   - The [relation contract](crm-relation-sync-contract.md) is now used by those dormant persistence/driver components, rather than only a standalone pure model. The actual API safeguards still deny outbound relation changes before mutation. See the repository-level relation-delivery and scalar-sync safety documents for implementation limits. BEIN relation-only unlink, provider CAS/exclusive-writer guarantees, verified mappings, old-worker transition, and explicit unknown/conflict recovery remain blockers. No production rollout or verified remote synchronization is implied.

4. CRM-specific frontend behavior for independent record actions and scoped-relationship 409 responses still needs the wider rollout review. The existing contact-directory browser regressions are distinct from full scoped-matrix UI acceptance.

The existing native CRUD, source-qualified directory, AI native action, WhatsApp identity and browser directory suites remain regression targets. Never use a production DSN or send test messages to real contacts.
