# CRM Smart Assistant

CRM Smart Assistant — веб-платформа BeinSystems для компаний, которые ведут
сделки в Kommo и хотят работать с задачами, клиентами, сотрудниками и
уведомлениями в одном кабинете.

## Два изолированных контура

- `/webapp` — существующий внутренний кабинет BeinSystems. Его данные и
  настройки не используются для клиентов платформы.
- `/register`, `/setup`, `/app` — кабинет нового клиента. Каждая компания
  получает собственный `tenant_id`; сделки, задачи, сообщения, уведомления,
  OAuth-токены и аудит изолированы на уровне PostgreSQL.

## Первый запуск клиента

1. Владелец регистрирует компанию через Telegram на `/register`.
2. AI-помощник помогает выбрать модули и сценарий работы.
3. Владелец подключает Kommo через OAuth и выбирает нужные воронки и этапы.
4. В `/app` появляются только выбранные данные Kommo; браузер читает быстрый
   кэш PostgreSQL, а не выполняет новый запрос к Kommo при каждом поиске.
5. Владелец создаёт ссылку приглашения сотрудника. Сотрудник подтверждает
   Telegram, владелец подтверждает запрос, и только после этого открывается
   доступ к кабинету. Telegram ID вручную не нужен.

## Railway variables

Никогда не храните реальные значения в Git. Полный перечень есть в
`.env.example`. Для нового клиентского контура обязательны:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | PostgreSQL Railway |
| `TENANT_ENCRYPTION_KEY` | Fernet-ключ для шифрования OAuth-токенов Kommo |
| `KOMMO_OAUTH_CLIENT_ID` | Public Kommo integration client ID |
| `KOMMO_OAUTH_CLIENT_SECRET` | Секрет public Kommo integration |
| `KOMMO_OAUTH_REDIRECT_URI` | `https://crm.pro.az/api/platform/integrations/kommo/callback` |
| `CANONICAL_WEB_ORIGIN` | `https://crm.pro.az` |

Старые переменные (`KOMMO_TOKEN`, WhatsApp, Telegram, VAPID и OpenAI) пока
нужны внутреннему BeinSystems-контуру и не должны переноситься в tenant-данные.

### Встроенный AI для AI Agents

Платформенный OpenAI-ключ остаётся только в Railway worker. Для включения
встроенного AI администратор платформы задаёт `AI_AGENTS_PLATFORM_ENABLED=true`,
`OPENAI_API_KEY` и центральный каталог `AI_AGENTS_PLATFORM_MODELS` (JSON-массив
идентификаторов моделей или объектов `{ "id", "label" }`).
`AI_AGENTS_PLATFORM_DEFAULT_MODEL` выбирает рекомендуемую модель. Клиенты не
видят ключ и не могут расширить каталог через API. Необязательные
`AI_AGENTS_PLATFORM_DEFAULT_TOKEN_LIMIT` и
`AI_AGENTS_PLATFORM_TENANT_TOKEN_LIMITS` (JSON `{tenant_id: limit}`) задают
дневные лимиты токенов; `0` означает отсутствие лимита. Существующая
интеграция «Çat üçün AI» остаётся совместимым источником для legacy-моделей.

## SaaS-аудит и целевая архитектура

Публичная документация с картой текущих жёстко заданных правил, моделью
tenant/роль/воронка, политиками задач и планом рефакторинга доступна по адресу
`/documentation` на основном домене.

## Ограничение блокировок при запуске

Полная подготовка схемы при запуске требует PostgreSQL 17 или новее: только
там доступен `transaction_timeout`. На более старом сервере запуск завершается
до выполнения DDL, без небезопасной замены общим `lock_timeout`.

Выделенное соединение миграции ограничивает каждую транзакцию пятью секундами,
а ожидание отдельной блокировки двумя секундами. Настройки сохраняются между
вложенными commit и не меняют рабочие соединения. Общая session advisory lock
сериализует запуски; закрытие соединения освобождает её и откатывает незавершённую
транзакцию, не скрывая исходную ошибку дополнительными rollback/unlock запросами.

Конфликты `40P01`, `40001`, `55P03` и завершение транзакции `25P04` допускают
до пяти попыток с новым соединением и паузами 1, 2, 3, 4 секунды. Другие ошибки
не повторяются. HTTP и фоновые задачи запускаются только после полной подготовки
и проверки схемы. Это ограничение одной транзакции, а не обещание завершить весь
запуск или любой запрос клиента за пять секунд. Проверка rolling deployment
также требует действующего старого worker до readiness нового и измерения
совместимости и задержек на восстановленной копии текущей базы.

Корневой `railway.toml` задаёт `healthcheckPath = "/health"` и
`healthcheckTimeout = 300`, сохраняя прежние команды сборки, запуска и restart.
По [документации Railway](https://docs.railway.com/deployments/healthchecks)
новый deployment получает трафик после успешной проверки, а до неё остаётся
активным предыдущий. Это не действует безусловно для сервисов с подключённым
volume и не является постоянным мониторингом после запуска.

Приложение слушает Railway `PORT` (по умолчанию 8080). Подготовка базы
завершается до старта HTTP, а HTTP entry point ещё раз проверяет committed schema
до привязки порта. `/health` доступен без авторизации для
`healthcheck.railway.app`; существующий redirect применяется только к старому
публичному Railway hostname. Во время следующего релиза необходимо проверить,
что Railway действительно использует корневую конфигурацию и эту healthcheck.
